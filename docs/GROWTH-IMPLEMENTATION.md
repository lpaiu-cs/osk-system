# Growth implementation — 2026-09-14

구현·검증 기록이다. 통치문서의 개정, 릴리스 선언, 운영 인스턴스 적용을 대신하지 않는다.
시작 기준은 main `c0969f123a242fdfcb3696c8c9f656e7fee92634`다.
PR #56의 계기·세션 키 수정은 별도 변경으로 유지했다.

## 해결한 단절

scope 기억의 길이를 줄이거나 그 해시가 바뀐 것을 지식 통합 완료로 삼으면,
원문을 읽어 노드에 남기는 단계가 생략될 수 있었다. 짧게 끝난 대화는 주기 알림까지
도달하지 못했고, Scope 노드를 Domain으로 비교할 실행 주체도 없었다.

1. Claude/Codex의 완료된 대화 라운드를 raw에 포착한다. 실제 하네스 대화 ID별로
   새 원문·검토 snapshot을 추적한다. 다른 대화의 scope 기억 쓰기로 대기를 지우지 않는다.
   Stop은 포착만 하며, 누락된 마지막 라운드는 알려진 전사를 다시 읽어 따라잡는다.
2. 기존 MCP 쓰기에 선택 인자 `distill`을 붙였다. 검색으로 기존 노드를 먼저 찾고,
   본문·선정한 근거·허브 연결의 실제 상태를 확인한다. 본문 저장 뒤 연결이 실패하면
   같은 작업 키로 이어가며 저장 성공과 통합 완료를 구별한다.
3. 전용 `growth run`이 미검토 대화와 Scope 비교 후보를 제한된 수로 고정한다.
   외부 에이전트가 의미를 판단하고 MCP로 저장한 뒤, 엔진이 검토 결정을 등록한다.
   이번 실행에서 새로 만든 Scope는 다음 실행부터 Domain 후보가 된다.

비교 대상 전체를 하나의 결론에 억지로 인용하지 않는다. 유용한 출처의 부분집합만
근거로 삼고 생략 이유를 남긴다. `no_value`·`summary`·`deferred`를 성장으로 세지 않는다.
근거와 허브의 기계 검사는 의미의 옳음을 증명하지 않는다.

## 구현 중 실제 모델로 확인한 경계

실제 Codex 프로세스와 실제 OSK MCP를 합성 mini-vault에 연결했다. 개인 vault나
실제 운영 훅 설정은 넘기지 않았다. 첫 실험의 입력·출력·소스 해시는 따로 고정하고,
수정한 구현은 두 번째 실험으로 분리했다.

| 실험 | 입력 유도 | 관측 | 해석 한계 |
|---|---|---|---|
| 첫 Scope | 일반 사용자 질문 + 생성된 통합 훅 문구의 재주입 | Scope 노드 1개, raw 출처 1개, 허브 연결 완료 | 실제 하네스의 자동 훅 실행 증거가 아니다 |
| 첫 Domain | 전용 성장 실행의 명시적 검토 지시 | Domain 노드 1개, 유효 출처 2개, 무관한 상자 규격 1개 제외 | 자발적 MCP 사용으로 집계하지 않는다 |
| 두 번째 Scope | 전용 실행에 미검토 raw 9개 제공 | Scope 노드 1개, 유효 raw 1개, 일회 상태 8개 제외, 최종 검토 등록 완료 | 전용 실행의 명시적 지시에 대한 반응이다 |
| 두 번째 Domain | 전용 실행에 Scope 3개 제공 | Domain 노드 1개, 유효 출처 2개, 무관한 출처 1개 제외, 최종 검토 등록 완료 | 최초 군집 생성·운영 자율성은 시험하지 않았다 |
| 최종 Scope | 최종 소스의 전용 실행에 raw 9개 제공 | snapshot·대상별 키 사용, Scope 1개와 검토 등록 완료, 173.3초 | 인자 오류 3회 수정 후 완료했다 |
| 최종 Domain | 최종 소스의 전용 실행에 Scope 3개 제공 | Domain 1개, 출처 2개·무관한 1개 제외, 검토 등록 완료, 65.7초 | 명시적 전용 실행이다 |

두 첫 실험에서 마지막 검토 CLI가 하네스 실행 정책에 막혔다. 엔진은 이 상태를
완료로 접지 않았다. 이를 계기로 모델이 최종 `osk_reviews` JSON을 반환하고 실행기가
기존 검토 API에 전달하는 경로를 추가했다. 모델의 셸 권한을 넓히지 않는다.

성공한 최종 응답만 읽으며 도구 결과 속 JSON·실패한 실행·다른 manifest·선정 외 대화는
받아들이지 않는다. 실제 저장이 없는 `preserved` 선언은 거부한다. Scope 저장 후 검토
등록만 유실된 경우에도 자기 raw에 연결된 기존 증거를 찾아 재사용한다.
전용 작업의 훅이 유지보수 대화를 다시 일반 대화로 포착하는 자기 반복도 차단했다.
실행기가 자식에 준 표시를 세 훅이 확인하며, 유지보수 증거는 해당 실행 기록에 남긴다.
두 번째 Scope 실행은 잘못된 `drafter` 대소문자와 해시 없는 source 객체로 두 차례
거부된 뒤 정상 형식으로 수정해 완료했다. 최종 성공을 무실패 실행으로 해석하지 않는다.
이 실행에서 대화 전체의 키를 증류 키로 사용한 것도 확인해, 이후 검토 키를 snapshot별로
구분했다. 같은 snapshot의 재시도는 같은 키, 새 관측은 새 키를 사용한다.

## 검증

정식 회귀 러너는 `_governance/_engine/tests/test_regression.py`이며 Python 3.11을 쓴다.
새 검사는 별도 subprocess mini-vault에서 실행하여 운영 vault와 엔진 전역 상태를 분리한다.

- 최종 전체 수트: **1,532 통과 / 0 실패 / 4 생략**, 164.1초. 생략은 Windows의
  POSIX 파일 권한 복원 검사 4개다.
- 새 격리 검사: distillation 21개, integration 27개, growth 19개 통과.
  전체 러너는 이 세 파일을 각각 한 묶음으로 호출하므로 전체 수치와 단순 합산하지 않는다.
- MCP 스키마: **7,492 / 7,500자**. surface lint와 SETUP 코드 일치 검사 정상.
  스케줄 등록 스크립트는 PowerShell AST 검사만 했으며 등록은 실행하지 않았다.
- 최종 실제 실험 두 건: **Scope·Domain 각각 preserved 등록 완료**.
  저장된 본문·출처·허브를 대조했고, 고정한 엔진 파일 해시가 현재 구현과 같음을 확인했다.
  원본 실패 실험과 수정 후 실험을 덮어쓰지 않고 별도 보관했다.
  커밋 전 파일 끝 빈줄 두 곳을 정리했으며, 시험한 엔진과 AST가 같음을 다시 확인했다.

최종 Scope의 중간 거부는 summary 80자 상한, 해시 없는 source 객체, `drafter=codex`였다.
모델은 같은 snapshot·대상 키로 인자를 고쳐 네 번째 쓰기에서 완료했다. 제약을 풀어
성공으로 만든 것이 아니며, 인자 형식 안내의 효율은 계속 관찰할 항목이다.

주요 실패 주입은 본문 저장 뒤 연결 실패, 응답 유실, 출처·목표 동시 변경, 동일 대화의
다른 root 재포착, 다른 대화의 기억 갱신, 잘못된 snapshot, 증거 없는 완료 선언이다.
Domain 비교는 보류 회전과 새·기존 출처 조합, 무관한 출처 생략을 확인한다.

## 남는 비용과 운영 선택

- **공유 지식을 기본으로 유지한다.** 독립 검토자가 기존 결론을 볼 수 있다.
  지식 연속성을 우선한다는 사용자 선택을 따른다. 독립성이 특별히 필요한 실험만
  고정 입력 vault와 새 하네스 문맥을 사용한다. 새 대화 ID 자체는 정보 격리가 아니다.
- 파일 전문 읽기 결과는 원본 참조로 남긴다. 복합 셸 출력은 파일 전문과 실험 결과를
  확실하게 나눌 수 없어 전사 위치·해시와 포착 범위 진단을 남긴다.
  **하네스 전사를 삭제하면 해당 상세 근거를 다시 읽지 못할 수 있다.** 현재 권고는
  원본 전사를 보관하고, 재사용하는 실험 근거는 증류 과정에서 필요한 범위를 별도로
  보존하는 것이다. 전량 복사의 정보 보존 이득과 레포 파일 전문 중복 보관 비용은 남는다.
- 대화별 대기와 재시도 저널은 기기 로컬 운영 상태다. raw와 노드는 공유하지만,
  다른 기기가 검토 대기까지 자동 인계받는다고 보장하지 않는다.
- 새 Domain 군집에는 기존 사용자 확인 규칙이 적용된다. 착지가 없으면 제안과
  확인 요청을 보류 사유로 남긴다. 합성 실험은 기존 Domain 허브를 준비했으므로,
  최초 군집을 무승인으로 만드는 자율성을 입증하지 않는다.
- 비교 목록 계산은 배치 수의 제곱까지 늘 수 있다. 모델에 주는 입력은 제한되며,
  현재 규모에서 별도 벡터 저장소나 검색 서비스를 추가하지 않았다.

운영 활성화는 정본 릴리스, 인스턴스 업데이트, 새 MCP 연결, 훅 신뢰·실행 확인,
전용 실행 명령 검증, 스케줄 등록 순으로 별도 진행한다. 이 구현 작업에서는 실행하지 않았다.
설정과 명령은 [SETUP.md](SETUP.md)에 있다. 배포 뒤 실제 자동 주입, 수동 저장 요청,
정기 전용 실행을 서로 다른 집단으로 집계해야 성장 효과를 판단할 수 있다.
