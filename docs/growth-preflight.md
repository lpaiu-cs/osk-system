# 성장 실행과 포착의 배포 전 점검

성장 실행의 `ok`는 고정한 선택 작업의 완료 여부다. 선택하지 않은 대화의
포착 실패는 `capture.ok`·`capture.errors`에 그대로 남고 선택 작업의 완료를
취소하지 않는다. 선택된 대화의 포착 실패·미완료 검토는 여전히 실행을 막는다.
최신 정기 실행이 선택 작업을 완료하지 못했거나 완료가 3일보다 오래되면,
세션 시작이 경고하고 Stop fork가 자기 scope의 근거 재검토를 맡는다.

2026-09-17 실 인스턴스 점검에서 실행 명령의 버전별 Codex 경로가 사라져 있었고,
정기 성장 작업은 비활성 상태였다. 실행 파일만 확인하는 `growth run --check`를
추가했다. 이 검사는 모델이나 MCP를 시작하지 않는다. 스케줄러 등록도 같은 검사를
먼저 거친다. 별도 API 공급자나 새로운 에이전트 실행기는 추가하지 않는다.

검사 결과의 경로는 심볼릭 링크를 해소하지 않고 절대화한다. `.venv/bin/python`을
시스템 Python으로 바꾸지 않기 위해서다. POSIX의 상대·빈 PATH 항목은 실제 실행
디렉터리인 vault를 기준으로 검색하고, Windows는 호출 프로세스 기준 검색을 유지한다
([Python의 실행 경로 규칙](https://docs.python.org/3/library/subprocess.html#subprocess.Popen)).

## 포착 오류의 근인

Codex native 전사의 `task_complete`에는 성공뿐 아니라 오류 종료가 들어온다.
goal 후속 턴은 일반 UserMessage 이벤트 없이 입력을 싣고, heartbeat는 하네스가
주입한 도구 결과로 시작하며 마지막 텍스트가 비어 있을 수 있다. 실패·중단 뒤
실행도 새 사용자 발화 없이 진행된다. 이들을 모두 '완료 내용 누락'으로 분류하면
종료된 작업의 관측이 증류 원료에 도달하지 못하고 영구 포착 오류로 남는다.

- 오류 종료는 `failed`, 종료 기록 없이 다음 task가 시작된 부분 기록은 `interrupted`로
  보존한다. 작업 성공이나 완전한 원문을 뜻하지 않는다. 열린 EOF 꼬리는 계속 대기한다.
- goal·heartbeat·실패나 중단 뒤 입력 없는 실행은 `native_trigger`로 명시한다. 앞 입력은
  문맥으로만 보존하며 같은 의도의 재개라고 확정하지 않는다. 새로운 사용자 발화로
  만들어내지 않는다.
- task/response의 대화·턴 식별 검사는 유지한다. task_complete 없는 final 텍스트,
  출처를 확인할 수 없는 무입력 실행을 정상 완료로 추정하지 않는다.
- 원문도 사용자 턴도 포착한 적 없는 시작 흔적은 `awaiting_native`로 따로 반환한다.
  상태를 삭제하거나 검토 완료로 바꾸지 않고, 제한된 성장 작업 슬롯에서 제외한다.
  파일 생성이 관측되면 다시 선택한다. 사용자 턴이나 이전 포착이 있던 원본의 소실은
  이 예외에 들어가지 않는다.
- 저장된 native 경로가 사라지면 같은 대화 ID의 기본 전사·보관 디렉터리에서 찾는다.
  후보가 여럿이면 자동 선택하지 않는다. 파일 안의 대화 ID와 기존 raw 접두부까지
  검증한다. 기존에 살아 있는 명시 경로는 유지한다.
- 아직 scope가 정해지지 않은 대화는 명시적으로 고른 안정적인 세션 키로 첫 착지를
  할 수 있다. 그 뒤 일반 cwd 키로 재개해도 같은 대화 ID의 착지만 사용하며, 그 일반
  키를 전역 결속하지 않는다. 다른 대화나 이미 정해진 다른 scope로는 옮기지 않는다.

## 기존 좌표와 검토 증거 보존

이미 저장된 raw의 v1·v2 직렬화는 그 판본으로 바이트를 대조한다. 새 포착은 v3 헤더에
native turn ID를 싣는다. 새 파서가 찾은 과거 턴은 기존 raw 뒤에 추가하므로 옛 번호,
출처 해시, 완료 영수증과 검토 커서를 바꾸지 않는다. 로컬 커서가 유실돼도 raw의
헤더로 append 순서를 복원한다. 내용 불일치 시 옛 codec으로 우회하지 않는다.

따라서 raw 번호 증가를 새로운 활동 또는 자율 성장으로 세면 안 된다. 복구된 과거
원문, 명시 지시 보존, 자동 포착, 후속 Scope/Domain 재사용을 따로 판독한다.

## v4.2 M2: 원본 경로의 복구와 저장된 raw의 검토

다른 전사 경로를 명시했을 때 기존 구현은 신원·접두부 검증보다 먼저 저장 경로를
교체했다. 다른 대화의 전사나 바뀐 접두부를 거부하더라도, 이후 경로를 생략한 재시도가
그 거부된 원본으로 돌아가는 결함을 익명 사례로 재현했다.

검증 중인 `capture_path`와 마지막으로 받아들인 `transcript_path`를 구분한다.
후보는 대화 신원과 저장된 raw 접두부를 모두 통과해야 확정 경로가 된다.
raw 재생 전 검증 거부에서는 후보를 지우고 이전 경로·원문 좌표·완료 영수증을
유지한다. raw 저장 뒤 커서 갱신에 실패하거나 I/O 오류로 저장 여부가 불확실하면
후보를 유지한다. 프로세스 중단과 마찬가지로 경로 없는 재시도·catchup이 남은 후보를
재생하여 새 경로의 추가분을 놓치거나 같은 라운드를 다시 저장하지 않는다. 복구 중
원본 읽기가 다시 실패해도 재시도 경로를 유지한다. 최초 포착의 아직 없는 파일과
열린 종료 꼬리에 대한 재시도 정보도 유지한다.

`integration capture/status/review`의 `capture_recovery`는 포착 상태와 다음 행동을
설명한다. `review`와 성장 worker의 선택 작업에는 `raw_review`도 포함한다.
이 값은 선택한 raw 범위의 좌표·해시를 재검증한 결과이며, 의미 품질이나 원본 전체의
완전성을 뜻하지 않는다. 이후 ACK와 보존 영수증 검증은 다시 수행한다.

| 관측 | 표시와 다음 행동 |
|---|---|
| 전사가 이동했고 같은 ID의 원본을 하나 찾음 | 기존 자동 재탐색으로 복구하고 접두부·이력을 보존 |
| 활동·포착 이력이 없는 원본 미생성 | `awaiting_input`; 같은 대화의 원본 생성 뒤 재시도 |
| 과거 원본 소실, 여러 후보, 신원 불일치, 착지 또는 접두부 문제 | `action_required`와 실패 단계; 올바른 원본·착지를 확인하며 기존 커서를 유지 |
| 오류 없는 열린 종료 꼬리 | `pending`; 종료 기록을 기다리고 미완료 꼬리를 ACK하지 않음 |
| 원본 포착은 실패했지만 선택한 저장 raw가 일치 | `raw_review.state=verified`; 그 완료 범위는 검토 가능하나 포착 실패는 계속 대기 |
| 선택한 raw가 없거나 해시가 바뀜 | `raw_review.state=unavailable`; 증류·ACK를 보류하고 원래 좌표·해시 복구 |
| 검토할 완료 raw가 없음 | `raw_review.state=none`; 원문 미관측을 `no_value`로 닫지 않음 |

원본이 없으면 도구 출력의 native 참조 등 저장 범위 밖의 근거를 복원했다고 주장하지
않는다. `no_value`는 실제로 검토한 raw에 남길 지식이 없다는 판단에만 사용한다.
저장 raw를 ACK해도 미해결 원본 포착이 완료로 바뀌지는 않는다.

`test_integration.py`는 잘못 지정한 원본 거부, 경로 교체 중 중단·I/O 실패·재생, raw 변조,
이동·신원·착지·열린 꼬리와 기존 좌표·해시·검토 이력 보존을 검사한다.
`test_integration_recovery.py`는 영수증 무효화와 분할 재검토를 재생한다.
`test_growth.py`는 Scope checkpoint 후 worker 실패와 재시도에서 완료 대화가 빠지고
미완료 대화만 다시 제시되는 것을 검사한다. 같은 하네스·구독·모델·권한과 연속 실패
fallback은 기존 `test_response_growth.py`의 계약을 유지한다. 이들은 각각 별도
프로세스로 실행하며, 모델 추론이나 실 인스턴스 복구를 수행하지 않는다.

ACK가 없는 Scope 후보의 순환 선택 결함은 M4에 남는다. 완료 checkpoint 보존과
선택 기회의 공정성은 별개의 기준이다. 인증 충돌에 대한 추가 재시도도 반복 재현 없이
도입하지 않는다.

## Codex fork와 구 상태의 재평가

Codex의 `history_base`는 페이지 경로와 끝 바이트를, `forked_from_id`는 부모 대화를 선언한다.
각 페이지의 신원·순환·유일 경로·바이트 경계를 확인한다. 같은 대화의 페이지는 이어 읽되,
부모와 자식의 턴은 따로 판독한다. 자식 이벤트로 부모의 미완료 턴을 끝내지 않는다.
부모 범위의 미완료 꼬리는 `coverage.ancestor_pending_tails`와 검토 안내에 남긴다.

같은 Scope에 부모 라운드가 이미 저장됐다면 native ID·기존 raw 해시·기록된 codec의 본문을
대조해 `inherited`로 참조한다. 자식 파일의 `codex-inherited-v1` 헤더는 커서 유실 뒤에도
이 관계를 유지한다. 부모의 ACK·미검토 대기는 그대로 두며, 다른 Scope의 raw는 재사용하지 않는다.
원본 부모 라운드가 저장된 적 없다면 검증된 history의 완료 라운드를 자식 raw에 보존한다.

`send_message_to_thread`가 전달한 기동 입력은 `native_trigger=thread_message`로 구별한다.
해당 namespace·도구 이름·현재 turn ID가 일치하고 call ID가 없는 native 전달만 해당한다.
일반 도구 결과와 다른 턴의 결과는 입력으로 해석하지 않는다. 사용자 발화 수로 세지 않는다.
이미 사용자 입력이나 재개 문맥이 있던 턴은 기존 codec을 유지해 저장된 raw의 바이트를 바꾸지 않는다.

실패 단계가 없는 구 커서는 오류 문구와 원본 재탐색으로 안내를 보완한다. `basis`는
`legacy_diagnostic`, `source_lookup`, `source_lookup_failed` 등 판정 근거를 표시한다.
원본 후보를 발견한 `retryable`도 복구 완료가 아니다. 입력·라운드·지문이 모두 비어 있어도
실제 원본이 존재할 수 있으므로 세 필드만으로 `awaiting_input`을 판정하지 않는다.
`growth status`는 대기 상태와 실패 단계의 분포를 읽으며, 조회로 capture·ACK를 수행하지 않는다.

`tests/test_codex_forks.py`는 페이지를 포함한 fork, 부모 raw·ACK·미검토 대기 보존,
커서 유실 재생, Scope 경계, 잘못된 부모·턴, 열린 부모 꼬리, 전달된 기동 메시지와 구 상태를
독립된 임시 vault에서 검증한다. 실제 복제본의 결과와 남은 조치는
[M2의 후속 복제본 재생](v4.2-milestones.md)에 기록한다.
운영 인스턴스 적용과 모델의 검토·보존은 이 시험에 포함하지 않는다.

## 검증 결과

정식 `tests/test_regression.py` 수트는 **1567 통과 / 실패 0 / Windows 권한 검사 생략 4**다.
익명 fixture는 실패·빈 heartbeat·중단·커서 유실·구 codec·원문 변조·전사 이동·대화 간
착지 격리를 검사한다. 실 데이터 복제본의 36개 상태 중 원문 미관측 10건은 대기로 남기고,
나머지 26건은 명시 착지 3건을 포함해 모두 오류 없이 재생했다. 기존 466라운드의 번호·해시·
검토 영수증을 유지하고 113라운드를 추가 포착했으며 재시도 추가는 0건이었다.
원료 밖 기존 492개 파일과 일반 세션 키의 결속은 바뀌지 않았다.

실 인스턴스 갱신·재시작·정기 작업 활성화·모델 호출은 이 검증에 포함하지 않는다.
이 수치는 보존 경로의 검증이며 의미적 증류 또는 자율 성장의 성공률이 아니다.

## 한 번의 배포로 묶기

PR63의 참조·조직 검토, PR64의 숨김 raw 저장, 이 포착·실행 수정의 검증을 마친 뒤
정식 릴리스와 인스턴스 갱신을 한 번 수행한다. 엔진 갱신 전까지 실 MCP·sync daemon과
스케줄러 상태를 유지한다. 실제 갱신 시 기존 writer 재시작 경계를 관리하고 raw
이관·구 좌표 해시·구독 로그인·MCP 쓰기·한정 성장 실행을 각각 확인한다.

기존 참조·허브 누락과 의미적 증류 대기는 별도의 데이터 정돈이다. 이에 필요한
노드 변경은 MCP로 수행하며 엔진을 다시 배포하거나 하네스를 재시작할 이유가 아니다.
