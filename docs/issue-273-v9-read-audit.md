# v9 반복 조회와 압축 관측 — 2026-11-06

원래 F01–F100, gpt-5.6-sol과 gpt-6.1-terra 각 100회, 총 200회의 저장된 events.jsonl을 분석했다. 새 모델 재실행은 하지 않았다. 원래 실험은 --ephemeral이므로 압축 원본 로그가 없으며, 압축 미발생으로 채점하지 않는다.

## 집계 기준과 결과

동일 도구·동일 인자·동일 성공 응답을 반복 조회로 센다. 다른 view와 변경된 응답은 제외한다. 도중 update 등 쓰기가 있었으면 별도 분류한다. 연속 중복은 두 도구 호출 사이에 다른 도구 호출이 없는 경우다. 모델의 사고나 압축으로 재조회가 필요했는지까지 이 지표가 증명하지는 않는다.

| 항목 | 5.6 Sol | 6.1 Terra |
|---|---:|---:|
| 전체 읽기 호출 | 247 | 233 |
| 동일 응답 재조회가 있는 실행 | 8/100 | 17/100 |
| 동일 응답 재조회 호출 | 12 | 21 |
| 사이에 쓰기가 없는 재조회 호출 | 11 | 19 |
| 연속 중복이 있는 실행 / 호출 | 4 / 4 | 8 / 8 |

쓰기 없는 재조회가 있는 실행도 각각 8회와 17회다. 합계 25/200회(12.5%), 30/480 읽기 호출(6.25%)이다. 연속 중복은 12/200회(6%), 12/480 읽기 호출(2.5%)이다. 두 모델 중 하나라도 동일 재조회가 있는 고유 fixture는 20개다. 이는 낭비 후보이며 확정 토큰 낭비율이 아니다.

- Sol 연속 중복: F13, F26, F67, F78.
- Terra 연속 중복: F26, F39, F67, F76, F78, F81, F91, F98.
- Sol 나머지 후보: F76, F83, F96, F98.
- Terra 나머지 후보: F04, F21, F24, F31, F33, F37, F47, F61, F70.

F13: 최초 두 문서 읽기 → 대상의 두 구간 읽기 → 대상 전문 두 번 읽기 → 저장 → 대상과 연결 문서 읽기. 동일 응답 재조회 3회 중 쓰기 없는 것은 2회, 연속 중복은 1회다. 저장 후 연결 문서 재조회는 보수적으로 낭비 후보에서 제외했다.

## 압축 가능성의 거친 추정

원본 이벤트에는 호출별 입력 토큰이나 압축 이벤트가 없다. 누적 input_tokens는 각 호출의 반복 입력을 합친 값이므로 컨텍스트 크기로 쓰지 않았다.

감사 스크립트는 프롬프트 및 직전까지의 완료된 도구/메시지 이벤트를 UTF-8 바이트로 합산한다. 이는 실제 모델 입력 토큰이 아니며, 숨은 시스템 입력·도구 정의·추론 내용은 빠지고 JSON 포장/중복 필드는 들어간 대용치다. 2–4바이트/토큰이라는 가정을 적용한 감도 범위만 본다. tokenizer 측정이나 확률 추정이 아니다.

- F13 Sol 연속 중복 직전: 239,798바이트 → 약 6만–12만 토큰 대용치.
- Sol의 쓰기 없는 재조회 직전 최댓값: F76, 318,522바이트 → 약 8만–15.9만.
- Terra 최댓값: F91, 412,805바이트 → 약 10.3만–20.6만.
- 현재 로컬 models_cache.json에는 Sol context_window 272,000, Terra 500,000, effective_context_window_percent 95가 기록되어 있다. 과거 실행의 실제 적용값이나 자동 압축 임계값을 증명하지 않는다.

이 가정 아래에는 용량 초과에 따른 압축이 연속 중복의 공통 원인이었을 가능성은 낮아 보인다. F13도 같은 판단이다. Sol F76 등 입력이 큰 사례는 상대적으로 의심을 더 남긴다. 숨은 입력·낮은 임계값·명시적 압축을 배제할 수 없고, 0건이라고 확정하지 않는다. 정확한 사후 복구는 불가능하다.

## 앞으로의 수집

사용자 결정에 따라 benchmarks/abstraction_v9.py의 기본값은 --ephemeral을 유지한다. --retain-trace를 명시한 진단 실행에서만 영구 로그를 수집한다. 해당 실행 완료 후 thread.started의 정확한 ID로 실행 날짜 주변의 세션 파일만 찾아 rollout.jsonl로 복사한다. compaction.json은 compacted/context_compacted 이벤트의 시각·순서와 token_count의 호출별 사용량/컨텍스트 창을 보존한다. 기본 실행의 compaction_count는 0이 아니라 null이다.

원본 파일을 찾지 못하면 missing 또는 ambiguous로 기록하고 compaction_count는 null로 남기며 경고한다. 0건과 수집 실패를 구분한다. 정상 압축 기록과 대응 알림이 둘 다 있으면 이중 집계하지 않는다. 기존 동결 실험 소스와 산출물은 변경하지 않았다. 향후 실험은 수정된 러너를 사용하거나 새로 동결해야 한다. 로그에는 실험 입력/응답이 들어가므로 기존 비공개 산출물과 함께 로컬에 보관한다.

검증: 압축 이벤트/알림 중복, 알림만 있는 경우, 이벤트 없는 기록, 원본 누락, 토큰 기록 보존, 다른 view/쓰기/본문 변경의 재조회 구별을 2개 단위시험으로 확인했다. 실제 모델을 다시 실행해 압축을 강제로 발생시키는 시험은 하지 않았다.

## 날짜와 diff 확인

현재 integration.cite의 인용 메타데이터는 harness/conversation/turn/source 및 내용 해시를 보존하지만 출처 타임스탬프를 넣지 않는다. 오래된 dialogue-v1도 원본 턴 식별자만 있다. 따라서 모든 출처에 정규화 날짜가 이미 존재한다는 전제로 날짜 렌더링을 엔진으로 넘길 수는 없다. 원본 로그의 명시적 시각을 정확한 턴과 연결해 보존하는 단계가 필요하고, 불가능한 과거 출처는 미상으로 유지해야 한다. 날짜 구현은 이번 작업에서 변경하지 않았다.

200개 실제 prompt.txt의 abstraction.commits가 각각 정확히 하나이며 해당 fixture의 unified diff와 일치함을 검사했다. +/-와 주변 문맥이 판단 입력이다. before_body/after_body 전문은 프롬프트에서 제거되어 있고 현재 문서는 read_node로 읽는다. 입력이 정확하다는 사실은 모델이 실제로 논지 변화를 정확히 분류했다는 보증은 아니다.

네 분류 제안: 결론·범위 변경 / 신뢰도 변경 / 논지 불변 / 미확정. 첫째에 새 논지 추가와 적용 조건 변경을 포함한다. 첫째와 둘째 모두 전체 보존, 셋째만 세부 처리, 넷째 보류. 두 변화가 겹치면 첫째를 우선한다. 단순 사례 증가만으로 신뢰도 변경을 자동 인정하지 않는다. 이 분류는 논의안이며 프롬프트에는 아직 반영하지 않았다.
