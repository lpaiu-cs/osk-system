# v6.0 구조 개편

엔진 코드를 다시 짜는 계획이다. 규범은 [코드 규범](CODE-STANDARD.md)에 있고, 이 문서는 순서와 끝의 기준을 적는다.

- 작성일: 2026-11-10. 사용자가 계획을 보고 0단계 착수를 정했다.
- 상태: 0단계 진행 중.
- 수치의 출처: v5.6.0(e177556d). 구조 수치는 `tests/test_architecture.py`가 잰 것이다.

## 방향

처음부터 다시 쓰지 않는다. 지금의 시험 수트를 안전망으로 삼아, 동작과 저장 형식을 바꾸지 않는 작은 단계로 엔진 전체를
다시 짠다. 규범은 문서가 아니라 시험이 강제한다.

- 시험 3만 줄이 넉 달 치 결함 이력이다. 새로 쓰면 그 결함들을 다시 만든다. 시험은 변경이 작을 때만 원인을 가리킨다.
- 구조 문제의 대부분은 **자리가 틀린 도우미**다. 모듈 머리의 import만 보면 순환이 없고, 함수 안 import까지 넣으면
  서로를 import하는 모듈 쌍이 22개다. 저수준 도우미가 고수준 모듈(`write`)에 살아서 생긴 일이라, 논리를 고치지 않고
  옮기면 풀린다.
- 다시 써야 할 만큼 나쁜 곳은 좁다. 본문 150줄을 넘는 함수 12개, 분기 50을 넘는 함수 10개다. 마지막에, 같은
  인터페이스 뒤에서 하나씩 다시 쓴다.

## 개편 내내 바꾸지 않는 것

- 저장 형식([FORMAT](FORMAT.md)), 대장 형식, MCP 도구 목록과 스키마, CLI 명령, 훅 출력 문구.
- 진입점의 파일 경로: `mcp_server.py`, `scripts/hooks/*.py`, `scripts/growth_run.py`, `scripts/setup.py`,
  `scripts/recover.py`, `sync_daemon.py`, `osk-cli.*`, 그리고 `python -m osk.cli`·`osk.update` 같은 모듈 진입점.
  사용자 기기의 하네스 설정과 OS 서비스가 이 경로를 부른다. 옮긴 뒤에는 얇은 위임으로 남긴다.
- 통치문서. 구조 개편은 조문을 고치지 않는다. 엔진 README의 "조문 → 모듈 매핑"만 새 구조로 고친다.
- 동작. 결함 수정은 개편 PR에 섞지 않는다([코드 규범](CODE-STANDARD.md) 12항).

## 안전망

- `v6.0-devel`로 가는 PR마다 CI가 Ubuntu(py3.11·3.12)에서 회귀 수트 전체를 돈다. 올리기 전에 로컬(Windows)에서도
  정식 회귀를 돈다. Windows·macOS를 포함한 전체 행렬은 릴리스 PR에서 돈다.
- 구조 시험의 기준선은 줄어들기만 한다.
- 업그레이드 행렬이 구 릴리스에서 후보로의 갱신을 본다. 파일이 대량으로 옮겨져도 갱신 뒤 저장소 상태가 같아야 한다.
- 이동·재구성 PR이 시험에서 바꿀 수 있는 것은 import 경로와 이름뿐이다.
- 표면 고정 시험(`tests/test_surface_snapshot.py`)이 MCP 도구의 설명·스키마·순서와 `osk` CLI의 명령·옵션을
  기록과 전문으로 대조한다. `osk.update` 같은 다른 진입점의 인자는 회귀 수트가 명령을 실제로 불러서 지킨다.

### 2단계 — 저장소를 값으로

  `OSK_VAULT_ROOT`를 읽어 한 번 연다.
- 저장소를 읽거나 쓰는 함수는 `vault`를 첫 인자로 받는다(2026-11-11 사용자 결정). "지금 열린 저장소"를 돌려주는
  접근자는 두지 않는다. 접근자는 고칠 곳이 적지만 전역이 이름만 바뀌어 남는다.
- 끝: import 시각에 저장소에서 계산해 고정하는 이름 0. 저장소가 필요한데 인자로 받지 않는 함수 0. 한 프로세스에서
  임시 저장소 둘에 노드를 쓰는 시험이 통과한다.
