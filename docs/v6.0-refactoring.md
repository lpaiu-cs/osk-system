# v6.0 구조 개편

엔진 코드를 다시 짜는 계획이다. 규범은 [코드 규범](CODE-STANDARD.md)에 있고, 이 문서는 순서와 끝의 기준을 적는다.

- 작성일: 2026-11-10. 사용자가 계획을 보고 0단계 착수를 정했다.
- 상태: 0단계 진행 중.
- 수치의 출처: v5.6.0(e177556d). 구조 수치는 `tests/test_architecture.py`가 잰 것이다.

## 방향

처음부터 다시 쓰지 않는다. 지금의 시험 수트를 안전망으로 삼아, 동작과 저장 형식을 바꾸지 않는 작은 단계로 엔진 전체를
다시 짠다. 규범은 문서가 아니라 시험이 강제한다.

- 시험 3만 줄이 넉 달 치 결함 이력이다. 새로 쓰면 그 결함들을 다시 만든다. 시험은 변경이 작을 때만 원인을 가리킨다.
- 구조 문제의 대부분은 **자리가 틀린 도우미**다. 모듈 머리의 import만 보면 순환이 없고, 함수 안 import까지 넣으면
  서로를 import하는 모듈 쌍이 22개다. 저수준 도우미가 고수준 모듈(`write`)에 살아서 생긴 일이라, 논리를 고치지 않고
  옮기면 풀린다.
- 다시 써야 할 만큼 나쁜 곳은 좁다. 본문 150줄을 넘는 함수 12개, 분기 50을 넘는 함수 10개다. 마지막에, 같은
  인터페이스 뒤에서 하나씩 다시 쓴다.

## 진단

| 문제 | 수치 |
|---|---|
| 저장소 루트가 import 시각에 전역으로 고정된다 | `core`가 import될 때 루트와 경로 상수를 정하고, 그 상수를 쓰는 곳이 약 520곳이다. 그래서 시험이 vault마다 프로세스를 따로 띄운다 |
| 층이 뒤집혀 있다 | 아래층이 위층을 import하는 줄 16개, 진입점 밖의 함수 안 import 139개, 순환에 든 모듈 32개 |
| 밑줄 이름이 사실상 공개 API다 | 다른 모듈의 `_이름`을 쓰는 곳 210곳 |
| 한 모듈에 책임이 여럿이다 | `write` 2,142줄, `integration` 1,968줄, `growth` 1,525줄, `update` 1,382줄, `approvals` 1,206줄 |
| 함수가 크다 | 60줄 또는 분기 15를 넘는 함수 119개. 분기 수 최대 136(`transcripts._claude`) |
| 예외가 넓다 | 넓은 예외 처리 125곳. 오류를 메시지 문자열로 가른다 |
| 시험이 내부에 묶여 있다 | 시험의 밑줄 이름 참조 약 400곳, `mock.patch` 약 130곳. 회귀 수트 한 파일이 1만 3천 줄이다 |
| 도구가 없다 | 린트·형식·타입 검사 설정이 없다 |

## 목표 구조

| 층 | 담는 것 | 지금의 출처 |
|---|---|---|
| `kernel` | 경로, 시각·식별자, 원자 쓰기, 잠금, 대장, 프로세스, 판본 관문 | `core`(가름), `_portalock`, `epoch`, `layout`, `write`의 원자 쓰기·잠금 |
| `model` | 노드 계약, 링크, 관측 줄 문법, 이름 이식성, 본문 정규화, 비밀값 필터 | `contract`, `evidence`의 문법, `write`의 이름·본문 규칙, `secrets`의 필터 |
| `store` | 색인, 인용 기록, scope 기억, 퇴출, 보호영역, 결속·라우팅, 하네스 어댑터와 전사 | `graph`, `raw`, `scope_memory`, `evictions`, `approvals`, `write`의 결속·라우팅, `harness`, `transcripts` |
| `service` | 노드 쓰기, 검색, 재검토, 조직, 증류, 검증기, 대화 검토, 성장, 배포, 설치 | `write`의 도구, `integration`, `growth*`, `validate`, `update`·`release`·`publish`, `setup` |
| `surface` | MCP 서버, CLI, 훅, 데몬. 얇은 변환층 | `mcp_server.py`, `cli.py`, `scripts/`, `sync_daemon.py` |

- 가르는 모듈은 책임이 여럿인 여덟이다: `write`, `integration`, `growth`, `core`, `update`, `approvals`, `validate`,
  `transcripts`. 나머지는 자리만 옮긴다.
- 전사 파서는 하네스 어댑터 옆으로 간다.
- 모듈별 층 배정은 구조 시험의 `LAYERS`가 전 모듈에 대해 못박는다.

## 개편 내내 바꾸지 않는 것

- 저장 형식([FORMAT](FORMAT.md)), 대장 형식, MCP 도구 목록과 스키마, CLI 명령, 훅 출력 문구.
- 진입점의 파일 경로: `mcp_server.py`, `scripts/hooks/*.py`, `scripts/growth_run.py`, `scripts/setup.py`,
  `scripts/recover.py`, `sync_daemon.py`, `osk-cli.*`, 그리고 `python -m osk.cli`·`osk.update` 같은 모듈 진입점.
  사용자 기기의 하네스 설정과 OS 서비스가 이 경로를 부른다. 옮긴 뒤에는 얇은 위임으로 남긴다.
- 통치문서. 구조 개편은 조문을 고치지 않는다. 엔진 README의 "조문 → 모듈 매핑"만 새 구조로 고친다.
- 동작. 결함 수정은 개편 PR에 섞지 않는다([코드 규범](CODE-STANDARD.md) 12항).

## 안전망

- `v6.0-devel`로 가는 PR마다 CI가 회귀 수트 전체를 돈다. 로컬에서도 정식 회귀를 돈다.
- 구조 시험의 기준선은 줄어들기만 한다.
- 업그레이드 행렬이 구 릴리스에서 후보로의 갱신을 본다. 파일이 대량으로 옮겨져도 갱신 뒤 저장소 상태가 같아야 한다.
- 이동·재구성 PR이 시험에서 바꿀 수 있는 것은 import 경로와 이름뿐이다.
- 표면 고정 시험(`tests/test_surface_snapshot.py`)이 MCP 도구의 설명·스키마·순서와 `osk` CLI의 명령·옵션을
  기록과 전문으로 대조한다. `osk.update` 같은 다른 진입점의 인자는 회귀 수트가 명령을 실제로 불러서 지킨다.

## 단계

각 단계는 구조 시험의 합계로 끝을 판정한다.

### 0단계 — 기준선과 규범

파일 이동도 동작 변경도 없다.

- [x] 구조 시험과 기준선 파일(`tests/test_architecture.py`, `tests/architecture_baseline.json`). 회귀 수트가 함께 돈다.
- [x] [코드 규범](CODE-STANDARD.md).
- [x] `v6.0-devel` PR의 CI.
- [x] 회귀 수트 기준선 기록(아래 "기준선").
- [x] 표면 고정 시험과 기록(`tests/test_surface_snapshot.py`, `tests/surface_snapshot.json`).
- [ ] `v6.0-devel` 브랜치.
- [ ] ruff 설정과 형식 일괄 적용. 열린 PR(#318, #300)이 닫힌 뒤에 커밋 하나로 하고, blame 무시 목록에 올린다.

### 1단계 — 자리 바로잡기

이동과 이름만 바꾼다.

- 밑줄로 숨긴 공개 API를 제 층으로 옮기고 밑줄을 뗀다. `write`의 원자 쓰기·잠금·본문 정규화·이름 규칙,
  `secrets.write_raw`, `evidence`의 문법, `sync_daemon`의 잠금 경로가 먼저다.
- 끝: `lazy_imports` 0, `private_access` 0(사유와 함께 예외 목록에 올린 것은 뺀다). 순환과 `upward_imports`는
  검증기가 진입점을 들여다보는 것(`validate → cli`, `validate → mcp_server`)만 남긴다.

### 2단계 — 저장소를 값으로

- `Vault`(루트와 파생 경로)를 들이고 `core`의 import 시각 상수를 없앤다. 진입점은 지금처럼 `OSK_VAULT_ROOT`를
  읽어 한 번 연다.
- 끝: import 시각의 경로 상수 0. 한 프로세스에서 임시 vault 둘을 여는 시험이 통과한다.

### 3단계 — 모듈 분해

한 PR에 한 모듈이다. 저자가 이미 그어 둔 절 경계대로 가른다(`write`는 직렬화·결속·군집 관문·라우팅·도구의 다섯 절이다).

- 끝: 1,200줄을 넘는 모듈 0, `two_module_cycles` 0, `tangled_modules` 0, `upward_imports` 0.

### 4단계 — 오류와 경계

- 오류 형을 들이고, 대장 판독이 손상과 일시적 실패를 다른 형으로 올리게 한다. 표면의 응답 변환을 한 곳으로 모은다.
- 사용자에게 보이는 문구가 달라지는 PR은 동작 변경으로 따로 낸다.
- 끝: `broad_except`가 경계 목록에만 있다. 문자열로 오류를 가르는 곳이 없다.

### 5단계 — 큰 함수 다시 쓰기

한 PR에 한 함수다.

- 시험이 두터운 것부터 한다. 전사 파서 둘(`_claude`, `_codex`)은 고정 입력과 출력의 대조 시험을 먼저 늘린 뒤 다시 쓴다.
- 안내 문안 조립(`integration.prompt`, `growth.prompt`)은 문안과 조립 코드를 가른다. `validate.run`은 규칙 등록부로 바꾼다.
- 끝: 본문 150줄을 넘는 함수 0, 분기 50을 넘는 함수 0.

### 6단계 — 시험 재편

- 회귀 수트를 주제별 파일로 가른다. 러너는 그대로 둔다.
- 제품 코드 안의 fixture를 시험으로 옮기고, 프로세스를 따로 띄울 까닭이 없어진 시험부터 한 프로세스로 바꾼다.
- 끝: 제품 코드의 fixture 0, 1,500줄을 넘는 시험 파일 0.

### 7단계 — 옛 형식 지원 걷기

결정 뒤에 한다. `doctor --migrate`가 깨끗한 인스턴스만 v6로 올린다는 전제로, 옛 자리 인용 기록과 옛 `## 근거`,
비노드 `derived-from`의 판독 코드를 걷는다. 통치문서 개정이 필요하다.

## 이 개편이 하지 않는 것

- 회상, 프로젝트 간 재사용, 성장 실행의 비용은 이 개편으로 나아지지 않는다. 나아지는 것은 유지보수성이다.
- 재사용 계측과 고정 과업 기준선(#19)은 구조와 무관하므로 개편을 기다리지 않는다.
- 지속 색인과 선제 회상(#245)은 3단계 뒤의 새 구조 위에서 만든다.

## 기준선

회귀 수트(`tests/test_regression.py`), v5.6.0의 깨끗한 사본, Windows 11, Python 3.12.9, 2026-11-10:

| 통과 | 실패 | 생략 | 실행 시간 |
|---:|---:|---:|---:|
| 2,314 | 0 | 7 | 10분 54초 |

생략 7건은 모두 Windows가 POSIX 권한과 디렉터리 fsync를 다루지 않아서 생긴 것이다. 구조 시험과 표면 고정 시험을
더한 뒤로는 통과가 둘 늘어 2,316이다.

구조 수치의 출발점은 [코드 규범](CODE-STANDARD.md)의 표에 있다.
