# v5.0.0 성장 경로 개선 마일스톤

v5.0.0은 대화가 포착된 뒤 검토·보존·연결·정돈을 거쳐 다음 작업에 쓰이는 경로를 완성한다.
v4.1.3에서 복구한 실행 경로를 출발점으로 삼고, 남은 실패를 재현한 뒤 기존 구현을 보완한다.
새 노드 수나 프로세스 종료 코드만으로 성장 완료를 선언하지 않는다.

- 판의 방향: v5 계열(v5.0.0–v5.2.0)은 견고함을 다진다. 성장 경로가 실패 없이 끝까지 가고(이 판),
  그 결과가 의미를 보존하며([v5.1.0](v5.1-milestones.md)), 다음 작업에서 실제로 쓰이는지
  ([v5.2.0](v5.2-milestones.md))를 닫는다. 기억 모델의 확장은 [v6.0.0](v6.0-milestones.md)이 맡는다
  (2026-10-07 사용자 결정).
- 판: 2026-10-07 사용자 결정으로 v4.2.0 대신 v5.0.0으로 낸다. 옛 엔진과 섞어 쓸 수 없는
  기록(판단하지 못한 재검토의 보류, PR #162)과 통치문서 개정의 비준을 담기 때문이다. 개발
  브랜치 `v4.2-devel`과 추적 이슈 #136은 이름을 그대로 쓴다. 사료
  `_governance/records/2026-10-04-cited-capture.md`가 "v4.2로 비준"이라 적은 개정도 v5.0.0으로
  비준한다.
- 개발 브랜치: `v4.2-devel`
- 기준: `main` / `v4.1.3`, `edf9523fe32c5d9a08ab41b95dd464b3d0fe433f`
- 작성일: 2026-10-03, 동기화: 2026-10-07(`v4.2-devel` `7bdec98b`, PR #164 병합 뒤). 진행과 결정은 [#136](https://github.com/lpaiu-cs/osk-system/issues/136)이 추적한다.
- 상태: M1은 [PR #128](https://github.com/lpaiu-cs/osk-system/pull/128)로 병합했다. M2·M3·M4는 일부 항목을 병합했고 남은 항목이 있다. 병합과 실 인스턴스 적용은 별도로 기록한다.
- 출시 조건: M1–M4다(2026-10-07 사용자 결정). M5는 [v5.1.0](v5.1-milestones.md), M6은
  [v5.2.0](v5.2-milestones.md)으로 옮겨 그 판의 완료 기준으로 다룬다. 이 판의 출시를 막지 않는다.
- 통치문서 개정은 v5.0.0 릴리스 선언으로 비준한다: 원본 턴 추적·인용 기록(PR #131), 헌법 1조 3항 선의 가정(PR #146), Mechanism §4-1 재검토 완료의 `rechecked`(PR #151), Mechanism §9-4 3항 두 검토의 역할과 허브 트리(PR #155), 시행령 §7 2항·Mechanism §4-1 4항 판단하지 못한 재검토의 보류(PR #162).
- 실행 범위: 기존 Stop 검토와 사용자가 명시적으로 실행하는 한정 일괄 검토. 예약 기능은 추가하거나 활성화하지 않는다.

## 출발점과 해결 범위

v4.1.3의 [PR #127](https://github.com/lpaiu-cs/osk-system/pull/127)은 Claude Desktop의
버전 아래 빌드 디렉터리 탐색, 선택하지 않은 대화의 포착 오류가 실행 전체를 실패로 만드는 판정,
실패·미완료 일괄 실행이 Stop 재검토를 막는 판정을 고쳤다.
v4.1.2의 최종 결과 파서 수정도 기준선에 포함한다. 이들을 새 마일스톤의 성과로 다시 세지 않는다.

앞선 운영 조사는 2026-09-26 05:42:35부터 2026-10-03 07:19:39까지의 KST 기록을 사용했다.
이는 v4.1.3 적용 전 관측이며, 적용 후 실패율을 뜻하지 않는다. 이 문서는 실패 유형과 검증 계획만
보존한다. 개인 전사, 노드 본문, 대화 식별자와 운영 원장은 공개 저장소에 싣지 않는다.

| 남은 문제 | 확인한 범위 | 다음 판단 |
|---|---|---|
| 포착 오류와 미검토 원문이 함께 누적 | 전사 소실·신원 불일치·착지 미정, 검토 대기를 관측 | 안전하게 복구할 수 있는 항목과 외부 조치가 필요한 항목을 분리 |
| 저장 후 출처·허브 연결 누락 | 실제 누락을 수동으로 보수 | 일반 쓰기·증류·이동 중 어느 경로가 검증을 빠져나갔는지 재현 |
| 오래된 퇴출·정돈·재검토 항목 잔존 | 기존 순환 선택과 checkpoint가 있어도 대기가 남음 | 선택되지 않음·실행 실패·의미 판단 보류를 나누어 검증 |
| 승격과 의미적 분화의 증거 부족 | 사용자 요청으로 만든 Domain과 이동 사례 확인 | 기존 노드 갱신, 새 주장, 구조 이동을 구별하여 평가 |
| 후속 작업의 개선 미입증 | 보존 영수증과 수동 보수는 확인 | 독립된 후속 작업에서 검색·본문 사용·결과를 검사 |

인증 토큰 갱신 충돌은 처음 한 번 관측했을 때 별도 추론 점검이 성공해 반복 결함으로 확정하지 않았다.
10-05 실측에서 2026-09-25 이후 Claude 작업자 실행 86회 중 14회(16%)가 같은 메시지로 추론 전에
끝나 반복 결함으로 확인했고, v4.1.6이 Stop fork를 60초 뒤 한 번 다시 띄우게 했다. 그 처리로
충분한지는 M2에서 관측한다.
오래된 MCP 연결이 새 파일을 적재하지 못한 상태 역시
디스크 배포와 실행 프로세스를 구분해서 확인할 항목이다.

## M1 성장 상태와 근거를 일치시킨다

기존 상태 조회와 원장 판독을 보완한다. 먼저 익명 fixture와 읽기 전용 보고서로 기준선을 고정하고,
필요한 필드가 실제로 없을 때만 기록 형식을 확장한다.

- [x] 포착 대상 대화, 포착한 미검토 라운드, 복구 검토, 조직 구간, 퇴출, 근거 재검토의 분모를 각각 표시한다. 포착하지 못한 꼬리를 검토 대기 라운드에 합치지 않는다.
- [x] 선택 작업 완료, 원문 저장, 지식 보존, 현재 연결, 의미 판단, 후속 재사용을 별도 결과로 낸다. `deferred`, `no_value`, 빈 선택, 오류 종료의 의미를 유지한다.
- [x] 근거 재검토의 기준선 등록·자동 이어받음·직접 판독한 `unchanged`·본문 `updated`·사용자 상신을 구별한다. 근거 제거·대상 소실로 닫힌 작업도 직접 판독 성공으로 세지 않는다.
- [x] 훅 기동, 사용자 지시, 명시 일괄 실행, 과거 예약 실행을 구별한다. 현재 코드의 `work_context="daily"`는 공용 일괄 경로이므로 실제 예약 기동의 증거로 쓰지 않는다.
- [x] 디스크 버전, 현재 MCP의 `engine_rev`·`engine_stale`, CLI 버전·인증·fallback 사유를 같은 관측 시점에 확인한다. 재연결 전 성공을 새 엔진 검증으로 집계하지 않는다.

완료 기준은 고정한 원장을 다시 읽었을 때 모든 집계가 개별 상태와 일치하고, 혼합 버전과 원인 미확인
사례를 따로 설명할 수 있는 것이다. 운영 백로그를 없애는 일은 이 단계의 완료 기준이 아니다.

M2 착수 기준선은 v4.1.3 적용 뒤인 2026-10-03 11:50:04–17:53:01 KST로 닫았다.
기간 내 실행은 Stop 문맥 2건(기록상 완료 1·미완료 1), 명시 일괄 실행은 0건이다.
이는 실행별 엔진 해시가 없는 과거 기록이다. 현재 잔량과 적용 후 신규 실패를 혼합하지
않으며, 이 표본으로 희귀 결함을 제외하지 않는다. 문제는 운영 재관측·고정 사례 재현·
과거 관측만 존재로 구분하고 재현된 결함의 수정은 추가 관측을 기다리지 않는다.

주요 접점: `osk/integration.py`, `osk/growth.py`, `osk/rechecks.py`, `osk/response_growth.py`,
기존 `overview`·상태 조회 표면.

구현의 판독 계약과 실행 방법은 [성장 상태 판독](growth-status.md)을 따른다.

## M2 원본 턴 추적과 중단된 검토를 안전하게 복구한다

기존 전사 재탐색, `repair_pending`, 분할 검토, 연속 실패 fallback을 먼저 재생한다.
원인을 재현한 항목에 한해서 구현을 고친다. 전사를 찾지 못했다는 사실 자체는 식별 검사를
완화하거나 임의의 다른 대화를 붙일 근거가 아니다.

2026-10-04 결정(PR #131, 10-05 병합·v5.0.0 비준 대기)은 세 경로를 구분한다. 기존 `_raw/`의 좌표·본문·검토
영수증은 그대로 유지한다. 새 턴은 기기 로컬 커서에 원본 신원·좌표·내용 해시로 추적한다.
노드에 인용·검증이 필요한 턴만 `cite_round`로 보존하며, 선택하지 않은 대화를 vault에 복사하지 않는다.

새 경로의 완료 항목은 다음 검증으로 닫는다. PR #129·#130의 저장 경로 시험 통과를 새 추적 경로의
검증으로 대신하지 않는다.

- [x] 전사 이동·소실, 신원·계보 불일치, 같은 턴 ID의 내용 변경, 착지 미정, 열린 꼬리를 재현한다. 실패 단계가 없는 구 상태도 저장된 사실과 실제 원본 재탐색으로 분류하고, 다음 행동과 재개 조건을 표시한다. 빈 필드만으로 입력 없음을 단정하지 않는다. 원인마다 기존 시험이 재현하고, 아래 복제본 재평가 표(PR #160)가 다음 행동과 재개 조건을 적는다. 결정이 필요했던 세 원인은 2026-10-07 사용자 결정으로 정했다.
- [x] 재추적·원본 턴 판독·ACK가 검토 대상 내용 해시를 일관되게 확인한다. 같은 ID의 내용이 바뀌면 옛 snapshot으로 완료하지 않으며, 읽지 못한 원본은 `no_value`로 닫지 않는다. 기존 raw 좌표·바이트·검토 커서·영수증은 보존한다.
- [x] Codex fork의 선언된 계보·페이지 신원·바이트 경계를 검증한다. 부모 턴은 부모의 검토 책임과 원본 신원을 유지하고 자식의 새 작업으로 중복 등록하지 않는다. 부모의 완료·미검토 턴, 열린 꼬리, 다른 Scope, 원본 커서 유실, 구 raw와 새 native 좌표가 섞인 경우를 각각 시험한다. ID 검사 완화만으로 허용하지 않는다.
- [x] 선택 인용의 재시도는 같은 좌표를 반환하고 중복 저장하지 않는다. 반환한 `user_by`·응답 해시·출처는 실제 저장본과 일치해야 한다. 열린 턴이 종료되거나 원본이 복구돼도 과거 인용을 조용히 검증 완료로 바꾸지 않는다. 저장된 정보와 새로 관측한 정보가 다르면 그 차이를 명시한다.
- [x] 작업자가 최종 결과 묶음을 내기 전, 실행기가 개별 결정을 적용하는 중, 적용 후 응답 전에 각각 중단시킨다. 이미 MCP로 저장된 본문·출처·허브·보존 영수증은 유지하고, 받지 못했거나 적용하지 못한 검토 결정을 완료로 세지 않는다. 다음 실행은 기존 영수증을 확인하고 미완료 선택만 다시 제시한다. 세 지점 모두 기존 기능으로 통과한다 — 제출 전은 기존 시험이, 적용 중·적용 뒤 응답 전은 새 시험이 덮는다(PR #156).
- [ ] 작업자는 MCP와 최종 결과 묶음으로 판단을 전달하고, 실행기는 지원되는 vault 환경에서 기존 검증을 거쳐 적용한다. 같은 하네스·구독·모델·권한 조건을 유지하며 다른 설치의 CLI나 대체 API로 성공을 만들지 않는다. CLI `growth checkpoint`는 수동 사용 경로로 구분한다. Codex 일괄 실행의 실제 관측에서 작업자는 MCP만 쓰고 셸을 쓰지 않았다(PR #159). Claude fork는 아래 인증 재시도 항목의 관측 창에서 같은 조건을 본다.
- [x] 12시간 이상 원본 변경이 없는 대화 중 미검토 턴만 명시 일괄 검토에 제시한다. 진행 중·이미 검토한 대화는 제외하고, 필요한 앞 문맥만 한 턴씩 읽는다. 추적한 턴을 모두 검토했을 때만 해당 대화의 user·Stop 계수를 새 주기로 전환한다. 스크립트로 돌린 `codex exec` 실행은 추적·검토하지 않는다(2026-10-04 사용자 결정).
- [x] 출처 정정은 일어난 시점에 등록한다. 정정하는 쪽이 영향받는 검토를 그 자리에서 다시 열고, 다시 연 검토는 정정 좌표와 그 출처를 쓴 노드를 지니고 작업자에게 간다(PR #139).
- [x] 원래 세션이 진술한 도구 결과는 그 세션의 보고로 받는다. 도구 출력의 한정 판독을 만드는 대신 원래 세션을 다시 감사하게 만든 지시문을 고쳤다(2026-10-06 사용자 결정, v4.1.8 PR #143, `v4.2-devel` PR #147). 효과 측정에서 도구 원문을 이유로 한 보류가 9건에서 0건이 됐다.

## M3 저장 뒤 출처와 허브 연결을 끝까지 검증한다

`distill`의 재개·영수증 검증은 이미 있다. 수동 보수한 누락을 익명 사례로 바꾸어 일반 MCP 쓰기,
증류 쓰기, 노드 이동 가운데 누락 경로를 특정한다. 모든 쓰기에 새 트랜잭션 계층을 추가하지 않는다.

- [x] 본문 저장 후 출처 또는 허브 갱신에서 중단시키고, 같은 작업 키로 연결을 재개한다. 보존한 본문을 잃거나 노드를 중복 생성하지 않아야 한다. 생성 경로는 기존 시험이, 갱신 경로는 새 시험이 덮는다 — 기존 기능으로 통과한다(PR #154).
- [x] 완료 판정 시 대상 본문, 실제로 사용한 근거, 현재 지역 허브와 상위 입구를 다시 읽는다. 저장 응답의 `ok`만으로 통합 검토를 승인하지 않는다. 영수증 판정은 지역 허브부터 최상위 Scope 허브까지 다시 읽고, 상위 입구가 끊기면 다시 pending이다(PR #154).
- [x] 일반 쓰기의 누락 안내와 기존 조직 검토가 빠진 연결을 다시 발견하는지 검증한다. `derived-from`이 없다는 이유만으로 모든 노드를 결함 처리하지 않고, 주장과 근거의 필요성을 판독한다. 조직 계획(`missing_links`)과 검증기(`orphans`)가 다시 찾고, 허브가 잇기 전에는 조직 검토가 완료되지 않는다(PR #154). 일반 쓰기는 안내 대신 엔진이 같은 쓰기에서 착지 군집의 허브부터 최상위 허브까지 걸고, 허브 쓰기가 실패하면 못 이은 허브를 `hub_links`로 알린다(2026-10-07 사용자 결정, PR #157).
- [x] 동일 군집 내 이동, 경계 이동, 본문 변경을 구별한다. ACK 때 출처·대상·출처 링크·허브를 확인하고, ACK 뒤에는 대상 소실·최상위 군집 이탈·출처 링크 삭제만 구조 신호로 보고한다. 검토를 다시 열지 않으며, 다시 여는 것은 저장 라운드의 정정(`integration reopen`)뿐이다(2026-10-05 사용자 결정, 영수증 재설계).
- [x] 이미 노드에 있는 주장에는 본문을 바꾸지 않고 근거만 결속한다(PR #139). 영수증을 받으려고 레포 세부나 검토 메타 문장을 덧붙이지 않는다.
- [ ] 주장 노드 끝의 `## 근거` 절에 `derived-from`의 비노드 근거를 `- 날짜 · 라운드 좌표 · 지지|반례|조건 — 한 줄` 형식으로 적는다(2026-10-05 사용자 결정). 작성 규칙은 작업자 지시와 FORMAT §2.2에 넣었다(PR #140). 좌표와 `derived-from`을 짝짓는 검증기와 시행령 단서는 PR #165가 맡는다.

완료 기준은 누락 사례와 중단 사례 모두에서 보존·배치 상태가 실제 파일과 일치하고, 복구 뒤의
영수증을 다시 읽어 검증할 수 있는 것이다. 이 재판독은 ACK 때까지의 검증이다. ACK 뒤에는 구조
신호만 보고하고 검토를 다시 열지 않으며, 본문 변경은 근거 재검토와 조직 검토가 맡는다.
의미의 옳음은 M5에서 따로 평가한다.

주요 접점: `osk/distillation.py`, `osk/write.py`, `osk/organization.py`;
[참조와 군집 조직의 지속 검토](GROWTH-INTEGRITY.md).

## M4 오래된 퇴출과 정돈 작업이 처리 기회를 얻는다

기존 다섯 작업 큐, 유한 작업 예산, 실행 순서 회전, 기록된 선택 시도를 활용한다.
작업자는 MCP로 내용을 읽고 보존하며, 검토 결정은 최종 결과 묶음으로 제출한다. 실행기가 기존
검증으로 적용하므로 작업자 CLI checkpoint를 전제로 하지 않는다. MCP 쓰기·보존 영수증과
실행기가 적용한 검토 결정은 따로 판독한다. 활동이 없는 Scope와 Domain은 명시 일괄 검토에서 다룬다.
Stop은 원 대화와 자기 Scope의 기존 허용 범위를 지킨다.

고정 사례에서 Scope 후보 두 개가 후보·조직 큐와 경쟁할 때 `limit=3`의 ACK 없는 실행
6회 모두 첫 대화만 선택되는 결함을 재현했다. `catchup`의 mtime 정렬이 기록된 선택 시도를 보지
않았기 때문이다. PR #152가 고쳤다. Scope 대기열은 지금 자리에서 고른 횟수가 적은 대화부터,
같으면 다음 미검토 턴이 이른 대화부터 고르고(2026-10-05 사용자 결정의 시간순), 작업을 만들지
못한 대화는 건너뛴다. 최종 묶음 없이 중단된 실행도 선택 시도에는 남는다.

- [x] 다섯 큐에 후보를 두 개씩 고정하고 한 큐의 첫 후보가 ACK·최종 결과 묶음 없이 계속 중단되는 fixture에서, 기본 `limit=3`의 다섯 번 실행 안에 각 큐와 뒤의 처리 가능한 후보가 적어도 한 번 선택되는지 검증한다. Scope 후보는 12시간 종료 조건을 충족시키며, 아직 진행 중인 대화의 제외와 구분한다. 이는 v5.0.0의 제안된 검증 기준이다. PR #152의 fixture 시험이 확인한다.
- [ ] 같은 노드를 건드리는 대화 사이의 처리 순서: 엔진 큐는 공정성(같은 자리의 선택 횟수) 다음이 시간순이다(PR #152). 최신 대화부터는 정보 회귀 위험이 있어 채택하지 않는다(2026-10-05 사용자 판단). 재편집 비용·정보 회귀·대기 감소의 측정은 남았다.
- [x] 퇴출은 기존 노드 통합·새 노드 보존·이유 있는 폐기·보류로 판정한다. 처분 영수증과 선택한 원문의 검토 결정을 함께 확인한다. 기존 시험과 실제 기록으로 확인했다. 실제 퇴출 10건 모두 처분과 판정·대상이 일치했다(PR #161).
- [x] 조직은 선택된 구간의 본문 해시와 판단 이유로 진척을 남긴다. 일부 구간 판독을 전체 군집 완료로 승격하지 않는다. 보류는 바뀌지 않은 판독 구간과 넘김을 남기고(PR #149), 바뀌었거나 고르지 않은 구간만 빼고 알린다(PR #150). 실제 조직 판독 구간 177개가 모두 판단 이유를 지녔다(PR #161).
- [x] 재검토는 노드와 바뀐 근거를 읽고 유지·수정·상신한다. 연쇄 수정 판단이 필요한 항목은 구체적인 수정안과 함께 상신한다. 기존 시험이 유지·수정과 연쇄 수정의 상신을 덮는다(PR #161). 판단하지 못한 재검토는 종결하지 않고 이유를 다음 재검토에 넘긴다(시행령 §7 2항, PR #162).
- [x] 변경 없는 보류를 다시 만났을 때 이유·마지막 시도·다음 대상을 보존한다. 해결된 작업이 반복 선택되거나 한 차단 항목이 전체 예산을 독점하는 경로를 고친다. Scope 큐의 독점은 PR #152가 고쳤다. 재검토의 보류(PR #162)로 다섯 큐가 모두 보류 이유와 멈춘 자리를 다음 작업에 `previous_deferral`로 넘긴다. 차단 항목 뒤의 후보가 선택되는지는 위 다섯 큐 fixture 시험이 확인한다.
- 보류의 부분 완료(설계)는 2026-10-07 사용자 보류로 [v5.1.0](v5.1-milestones.md#미룬-설계)으로 옮겼다.

판정 경계는 선의 가정(헌법 1조 3항, PR #146)에 맞췄다(2026-10-06 사용자 승인).
- 보류는 아무것도 닫지 않으므로 낡음을 이유로 거절하지 않는다. snapshot 일치는 완료를 주장할 때만 요구한다.
- 결과 묶음은 항목별로 받는다(PR #150).
- 옛 선택의 보고가 늦게 붙어도 새 판정을 되돌리지 않는다. 앞 선택을 인과로 이은 선택의 보고가 판정을 정한다(PR #150).
- 재검토 완료는 `rechecked`로 적는다(PR #151).

완료 기준은 고정 후보 집합에서 처리 가능한 항목이 예산 안에 진척하고, 남은 항목마다 보류 이유와
재개 조건이 있는 것이다. 신규 입력이 계속 들어오는 운영 총량의 0건 달성을 요구하지 않는다.

주요 접점: `osk/growth.py`, `osk/evictions.py`, `osk/organization.py`, `osk/rechecks.py`;
[기존 실행 복구와 오래된 퇴출 처리](growth-execution-repairs.md). 해당 문서의 CLI checkpoint는 수동 경로이며 작업자 지시로 재사용하지 않는다.

## 구현과 릴리스 완료 기준

각 단계는 작은 PR로 나누고 문제·재현 입력·수정·독립 재판독 결과를 남긴다.
문서와 익명 fixture를 먼저 고정하고, 기존 기능으로 통과하는 항목에는 구현을 추가하지 않는다.
이번 계획에서 엔진 버전이나 `release.json`을 변경하지 않는다.

- 엔진 변경은 해당 회귀 시험과 `_governance/_engine/tests/test_regression.py` 정식 러너로 검증한다. 새 파일이 필요한 시험은 Git 추적 목록에도 포함한다.
- 정식 배포 전 기존 5개 CI 환경과 업그레이드 행렬을 통과한다. v4.1.3에서의 실제 업그레이드 출발 셀을 포함하고, 레거시 레이아웃을 유지한다.
- Actions 한도로 PR별 CI를 생략한 변경(PR #131 이후)에는 로컬 Windows 정식 러너 기록만 있다. 이를 5개 환경 통과로 적지 않고, 릴리스 전에 합본을 다시 검증해 실제 검사한 SHA·환경을 남긴다. 출시 직전 최종 SHA로 Actions를 한 번 돌려 5개 환경을 확인한다(2026-10-07 사용자 결정).
- 코드·형식 변경의 검증 결과와 운영 관측 결과를 따로 기록한다. M1–M4에 속한 운영 관측(예: M2의 인증 재시도 관측)이 남은 후보는 `devel` 또는 시험판 상태로 두고 성장 검증 완료로 표시하지 않는다. M6의 관측은 v5.2.0에서 다루며 이 판의 출시를 막지 않는다. M2 관측의 창과 판정 기준은 M2의 인증 재시도 항목에 있다.
- 출시 전에 통치문서 정합성을 점검한다(#42). 이번 판에서 개정한 조문 사이의 표기, `updated`, 교차 참조를 맞춘다.
- 최종 완료 보고에는 코드 SHA, 배포 버전, 실제 실행 엔진, 관측 창, 제외 항목, 미결 원인을 적는다. 적용은 기존 내용 결속 갱신 절차를 따른다.

위의 `osk/` 경로는 모두 `_governance/_engine/osk/`를 기준으로 한다.
