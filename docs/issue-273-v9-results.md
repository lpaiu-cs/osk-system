# v9 추상화·재검토: Sol / Terra 실험

2026-11-06. 수정된 v9 엔진으로 66회 실행을 완료했다. 이 개발 표본에서는 Terra를 재검토의 1차 수행 모델로 사용할 근거가 있다. Sol보다 빨랐고 출력 토큰도 적었으며, 확인되지 않은 세부는 더 보수적으로 남겼다. 다만 자동 정리의 완결성이나 반복 안정성까지 입증한 결과는 아니다.

## 의미 판독에서 확인한 차이

| 사례 | Sol | Terra | 판독 |
| --- | --- | --- | --- |
| F02·F08·F13 | 보존 | 보존 | 사전 기준은 정리지만 새 조건·한계·이유가 포함됐다는 보존 근거가 있다. 원래 행동 불일치는 그대로 남기고 명백한 오답으로 단정하지 않는다. F08에는 필요한 수치와 e-fold 비교가 실제로 전달됐다. |

| F31 | 실행·시험·산출물 기록 삭제 | 동결 순서는 날짜 미확인으로 보류, 시험·산출물은 근거 역할 미확인으로 보존 | **Sol의 v9 삭제 조건 위반.** 비노드 대화 #7에만 있는 상세를 삭제했다. Terra는 출처를 찾았으나 정리가 남았다. 옛 실험의 출처 탐색 누락과 구분한다. |

F26·F31에서 참조하는 다른 기억 문서 전문에는 삭제한 핵심 수치·산출물이 없었고 target에도 기존 근거 절이 없었다. 따라서 v9의 ‘다른 기억 문서 또는 기존 근거 줄에 모두 있으면 삭제’ 조건을 충족하지 않는다. 원 대화 기록은 남아 있으므로 전면적인 원자료 소실이라는 뜻은 아니다. v8의 copy 정답을 v9에 그대로 적용하지 않았다.

사전 보존군 20건의 실제 본문 보존은 Sol 19건, Terra 20건이다. 경계군 7건은 모두 따로 두었고 최종 정확도 분모로 옮기지 않았다. 모든 실행의 원래 diff·저장 diff·최종 이유를 읽고, 변경된 네 사례(F04·F18·F26·F31)의 출처와 저장 범위를 대조했다. 이 판독은 담당 에이전트의 단일 평가이며 독립 평가자 간 일치도는 재지 않았다. 후속 node 재검토는 기록 확인과 대표 사례 확인이며 모든 주장을 별도로 전수 검증한 것은 아니다.

## 입력과 read_cited

지시문은 v8 16,640자에서 최종 v9 3,358자로 약 79.8% 줄었다. 자료를 합친 최초 입력의 중앙값은 29,748자에서 27,090자로 약 8.9% 감소했다. 이는 글자 수 비교이며 한국어 전환의 토큰 절감률이 아니다. F24·F25처럼 전체 출처 목록을 복구해 오히려 길어진 사례도 있다. 지시문을 줄이는 것과 증거량을 줄이는 것은 별개의 문제다.

33작업의 출처 항목 347개(작업 간 반복 참조 포함)는 모두 해석 가능했다. 최대 발췌는 6,178자였고 알려진 알림·메타데이터 89,818자를 제외했다. 문자 일치가 없는 F13의 한 출처는 빈 발췌와 no_match로 표시했다. 두 모델의 작업 입력 불일치는 0건이었다.

Sol은 추가 read_cited 호출이 없었다. Terra는 F04 2회, F27 1회, F31 1회 사용했다. F04에서 기록이 아닌 참조 파일을 read_cited로 읽으려 한 실패 1회와 같은 파일의 read_node 실패 1회가 있었다. F31의 기본 조회는 다시 선별·잘린 2,487자를 반환했다. 따라서 read_cited를 항상 전문 펼치기로 해석하면 안 된다. 빈 검색을 반복하는 루프는 관측되지 않았고, 남은 난점은 출처 날짜와 이동할 근거 역할의 확인이었다.

## 검사 오탐의 정정

최종 모델 실행 동안 엔진·프롬프트·입력을 동결했고 종료 뒤 해시를 확인했다. 그 후 선택 출처의 read_ref(전체 경로)와 coordinate(축약 좌표)를 같은 대상으로 정규화하도록 검사기만 수정했다. 선택하지 않은 다른 라운드는 여전히 거절하는 회귀 시험도 통과했다.

F04 Sol의 저장 결과·모델 응답·도구 로그를 해시로 고정한 채 역사적 복제본에 실제 저장 diff를 복구하고 엔진 검사를 다시 적용했다. 초기 32/33이 33/33으로 정정됐다. 원 verification.json은 보존했고 verification-corrected.json과 verification-recheck.json에 재검증 결과를 분리했다. 이 정정은 날짜 귀속이나 의미적 완전성을 자동 승인하지 않는다.

## 비교 계약

[실행 전 기준](issue-273-v9-experiment.md)에 따라 `gpt-5.6-sol`과 `gpt-6.1-terra`를 medium으로 각각 33사례 × 1회 실행했다. 모델 순서를 교차 배치하고 순차 실행했으며 Astra는 호출하지 않았다. 운영 vault를 역사적 커밋별로 독립 복제하고 개발 엔진을 연결했으며 운영 설치본은 수정하지 않았다.

예비 실행은 별도 보존했다. PATH의 Codex CLI 0.154.0이 Terra를 거절하여 앱에 이미 설치된 0.166.0-alpha.6으로 실행 파일을 바꿨다. 사용자가 설치하거나 설정을 바꿀 일은 없다. 초기 `study/`에서 시스템 알림 정돈 누락을 발견했다. 그 뒤 `study-clean/`에서는 `[[문서명]]` 근거 참조를 조회용 이름처럼 준 오류를 발견했다. F24 Terra가 조회 실패 후 실제 보류했고 다른 사례에도 불필요한 재조회가 생겼다. 이를 수정해 `study-final/`에서 전 사례를 다시 실행했다. 앞선 결과는 정식 수치에 합산하지 않았다. 원래의 2회 반복 계획과 변경 전 엔진은 해시 일치 사본으로 보존했으며 최종 비교는 한 차례씩이므로 반복 안정성 수치를 내지 않는다.

## 실제로 바뀐 범위

- `prompt_version="v9"`인 재검토 전용 작업에 한국어 지침을 선택한다. 추상화 유무에 따라 전문·결과 형식이 달라진다.
- 변경 diff는 한 번만 전달하고 전체 출처 좌표를 유지한다. 긴 출처는 diff의 문자 일치 주변 ±2행을 골라 기본 6,000자, 첫 문맥 창의 확장 상한 8,000자로 제한한다. Markdown 표의 가까운 머리 두 행은 함께 선택한다. 의미상 필요한 모든 조건·단위를 찾는다는 보장은 없다.
- 앞부분으로 대체하지 않으며 일치가 없으면 `no_match`를 표시한다. 원문 해시·길이·구간 위치·생략 여부를 남긴다. 알려진 메타데이터·연결 알림은 제외하되 명령 결과와 사용자 정정은 보존한다.
- `_raw`, `_cited`, UUID가 아닌 기록 이름을 같은 해석 경로로 처리한다. `read_cited` 자체의 검색·반환 방식은 바꾸지 않았다.
- 근거 참조 `target`과 도구에 넘길 문서 이름 `target_name`을 구별해 링크 괄호·별칭·절 좌표를 문서 이름으로 잘못 전달하지 않게 했다.
- 엔진이 실제 저장 변경의 범위, 인용 좌표, 결과 형식, 재검토 기록과 현재 문서 상태를 검사한다. 의미 보존이나 출처가 주장을 뒷받침하는지는 자동 증명하지 않는다.
- 해시 충돌 뒤 재조회·재판단 안내는 오류 응답으로 옮겼다. 과거 보류와 현재 변경의 대응은 확정 가능한 경우만 표시한다.

## 수치를 읽는 방법

엔진 완료는 작업 기록과 저장 상태 검사를 통과했다는 뜻이다. 정답률이 아니다. 사전 고정한 26사례의 보존/정리 방향 일치와 경계 7사례를 분리하며, 저장 diff와 모델의 이유는 별도로 판독한다. 원래 기준에 문제가 드러나도 행동 일치 집계를 사후 유리하게 바꾸지 않는다.

시간은 CLI 모델 실행 구간으로, 복제본 준비·결과 검증 시간은 제외한다. 토큰은 CLI가 보고한 여러 요청의 누적 사용량이며 프롬프트 한 번의 길이가 아니다. 캐시 입력은 총 입력에 포함되고 추론 출력은 출력 토큰에 포함되므로 중복 합산하지 않는다. 구독 환경의 관측치로 금액이나 모델 가격을 추정하지 않는다.

## 산출물과 재현

실행기 `benchmarks/abstraction_v9.py`, 보고서 생성기 `benchmarks/abstraction_v9_report.py`를 사용한다. 비공개 fixture와 원문·결과는 저장소 밖 로컬 작업 폴더에 보존했다. `frozen-inputs.json`은 엔진·실행기·지시문·사전 기준의 SHA-256을 기록하며 `frozen-source/`에 해당 파일 사본도 있다. 실행별로 입력, 원래 문서, 저장 후 문서, 도구 이벤트, 결과 JSON, 실제 vault diff와 검증 기록을 남긴다.

## 검증 범위와 남은 한계

새 엔진 시험 10개 통과. 기존 growth 시험은 68개 통과·2개 건너뜀, growth_status 시험은 13개 통과·1개 건너뜀이다. 새 시험을 정식 회귀 목록에도 등록했다. 전체 릴리스 회귀·운영 배포는 이번 범위가 아니다. 재검토 외 업무의 프롬프트 분리, 일반 작업의 독립 묶음 자동 생성·병렬화, 실제 연속 세션의 보류 재처리는 측정하지 않았다. 같은 33개 개발 사례의 한 차례 비교이며 새 업무 전반의 성능이나 한국어·업무 분리 각각의 인과 효과로 확대하지 않는다.
