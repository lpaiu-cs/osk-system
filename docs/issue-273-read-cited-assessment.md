# read_cited의 실제 사용성과 실험 입력 문제

2026-11-05. 기존 실행 기록·실험 생성기·도구 구현의 정적 검사와 작은 로컬 재현으로 평가했다. 모델 재실험과 운영 수정은 하지 않았다.

## 사용자 판단 반영

6,000자 상한의 목적은 지나치게 긴 대화 라운드에 대한 방어다. 상한 자체의 제거가 아니라 재검토 diff와 관련된 주변 문맥을 선택하는 방식으로 개선한다. F08은 실험 설계 문제에 따른 재채점 대상이다.

## 세 가지 문제를 분리해야 한다

1. 초기 실험 입력·정답 생성기가 `_cited`만 찾고 레거시 `_raw`를 놓쳤다. Claude 원대화 2026-11-04T15:36:51Z의 보고가 이 문제를 명시한다. 수행자는 read_cited로 빠진 출처를 찾을 수 있었는데 정답 작성자는 못 봤으므로, 초기 실패 집계의 신뢰성에 중대한 영향을 줬다. 당시 보고의 ‘필수 위반 12건’은 오류 판정의 증거가 아니라 오염된 초기 채점 결과다. 이후 생성기는 두 경로를 찾도록 바뀌었다.
2. 수정 후에도 `job.py:65`는 `t[:6000]`, 68행은 마지막 20개 출처만 전달한다. F08의 문제는 이 조용한 앞부분 절단이다. 관련 내용을 검색한 read_cited 자체가 고장 난 것은 아니다.
3. 실제 read_cited에도 사용성 제약이 있다. query는 한 라운드의 같은 이벤트 안에서 공백으로 나눈 검색어가 모두 등장해야 하는 AND 검색이다. 검색 결과도 이벤트당 약 1,200자로 잘리고, 첫 검색어 위치 앞 180자부터 보여 준다. 여러 검색어가 먼 곳에 있으면 검색에는 성공해도 뒤 검색어는 반환 구간 밖에 있을 수 있다. 합성 문자열 ALPHA + 긴 padding + OMEGA로 이 현상을 재현했다. 이는 실험에서 그 오류가 발생했다는 뜻은 아니며 구조적 한계의 별도 확인이다.

## 영향과 남용 평가

v8 132회 중 18회(15개 fixture)에서 read_cited 사용. 총 49호출: query 19, 기본 조회 30, 빈 본문 9, truncated 11. 같은 실행 안 동일 인자의 반복 호출 0. 이 통계는 호출 이벤트에서 계산했으며 토큰 비용 측정은 아니다.

- F08 sol1: 8호출 중 6회 빈 결과. 서로 다른 라운드에 있는 내용을 긴 AND 질의 하나에 묶었다가, 셀 크기가 없는 #13에서 표현을 여러 번 바꿔 검색했다. ‘57’의 비어 있지 않은 결과도 원하는 셀 크기의 확인으로 취급할 수 없다. 추가 조회 필요성은 실제였으나 검색 전략은 비효율적이었다.
- F08 astra: 4호출로 #13의 중간 수치, #12의 셀 크기를 찾았다. 추가 조회가 복구 경로로 작동했다.
- F08 sol2/3: 추가 조회 없이 보존. 실험 입력의 잘림이 실제 처리를 놓치는 데 영향을 줬다. 정보 소실을 일으킨 치명적 쓰기 실패로 확인된 것은 아니다.
- F14 astra: 8호출, 작업 cited는 빈 사전. 생성기의 UUID 전제와 맞지 않는 Kiro 이름 기록이 대상 derived-from에 있었다. 8회 조회 자체를 남용이라고 할 근거는 부족하다. 기록 목록을 입력에서 빠뜨린 비용이다.
- F21 astra: 8호출. 입력에는 마지막 20개 출처만 있고 앞부분의 출처를 별도로 읽었다. 제공 범위 밖의 출처 확인이 포함되므로 횟수만으로 남용 판정하지 않는다. 확정적인 부재를 증명하려 모든 기록을 훑는 비용은 피해야 한다.
- F19 sol2/3: 이미 입력에 있던 짧은 #29를 각각 한 번 재조회했다. 실질 신규 정보가 거의 없는 중복 확인 후보다. 전반적 반복 루프는 아니다.
- F31 astra: 이미 입력에 있던 출처를 한 번 다시 읽어 확인했다. 중복 비용은 있지만 삭제 전 근거 확인이며 남용으로 단정하기 어렵다. sol2는 있는 내용을 놓쳤다.

v8에서는 read_cited의 오류 응답이 없었다. 초기 runs_v1/v2/v3에는 라운드 번호 없는 경로에 query를 보내거나 세션 기록 아닌 참조 파일을 넣어 거부된 호출이 각각 2/7/2회 있었다. v6/v7/v8은 0회다. 이는 ‘도구가 접힌 내용을 전혀 못 열었다’와 다른 문제다.

## 에이전트 친화성 판단

강점: 원문 전체에서 선택 검색, 출력량 상한, 출처 해시 유지, 선택·잘림 표시, 도구 추적과 불투명 추론을 기본 결과에서 제외. F08의 실제 복구 사례가 있다.

약점: ‘펼치기’가 일반적인 이어보기와 다르다. 다시 선별해 반환하기 때문에 max_chars를 높여도 review 총 6,000자·이벤트 약 1,200자 제한이 남는다. 같은 이벤트 AND 검색과 용어·숫자 표기 차이는 에이전트가 알아야 하는 부담이다. 검색 결과 0은 해당 질의가 그 라운드의 이벤트에 맞지 않았다는 뜻이지 사실 부재가 아니다. 전체 기록 경로와 정확한 라운드 주소, 비세션 파일은 서로 다른 처리가 필요하다. 실험 생성기의 단순 문자열 입력은 이 도구의 잘림 정보를 잃게 했다.

판정: 기능은 복구에 유효하지만, 재검토 작업에 처음부터 필요한 증거를 제공하는 흐름은 에이전트 친화적이지 않았다. 전면 교체보다 입력 선택과 조회 연결을 먼저 고치는 것이 적절하다.

## 최소 개선안

- 문서 diff의 추가·변경 주장에 맞춰 출처 안의 여러 관련 구간을 선택한다. 문서 diff의 줄번호를 대화 원문의 줄번호처럼 사용하지 않는다.
- 각 구간에 출처 좌표·원문 해시·원문 길이·선택 위치·생략 여부를 붙인다. 전체 출처 목록은 유지하고 본문 발췌만 제한한다. 어떤 기록이 빠졌는지도 드러낸다.
- 관련 구간의 앞뒤 문장, 표 헤더, 단위, 조건·반례를 함께 포함한다. 관련 구간이 여러 개면 병합하거나 여러 창으로 보여 준다. 아무 일치가 없으면 임의의 head를 완전한 근거처럼 제시하지 않는다.
- 평소 작은 예산을 사용하되 관련 주장을 온전히 담아야 할 때만 늘리고 총 상한을 둔다. 정확한 숫자는 이번 점검에서 새로 정하지 않는다.
- 초기 선택에 없는 주장만 read_cited로 추가 확인한다. 한 라운드에서 빈 검색을 반복하기보다 연결된 다른 출처로 넘어갈 수 있게 한다. 검색으로 못 찾으면 ‘출처 없음’ 대신 ‘이번 조회로 확인 못 함’으로 보류할 수 있게 한다.
- 쿼리 결과에 매치한 구간이 실제로 보이도록 여러 hit window를 제공하는 것을 검토한다. 먼저 기존 구현의 선택 기능을 재사용하고, 별도 검색 프레임워크를 도입하지 않는다.

## F31의 copy와 M1/M2/M3

copy는 추가된 내용이 문서의 새 논지가 아니라 기존 출처에 이미 있는 세부라는 정답 분류다. 출처에 모든 사실이 있으면 본문 중복을 정리하라는 뜻이다. 새 추상적 문장을 반드시 만들어야 한다는 뜻은 아니다.

- M1: 수정하면서 허용 범위 밖을 건드렸는가. 무변경이면 통과한다.
- M2: 추가·수정한 근거 줄이 정한 형식과 추가 좌표 조건을 지키는가. 새 근거 줄이 없으면 통과한다. 의미적 무손실 검사는 아니다.
- M3: 정답이 thesis/mixed/sourceless일 때 아무것도 바꾸지 않았는가. copy/movable에는 미적용이다.

따라서 F31 sol2의 kept는 M1/M2 통과, M3 미적용이어도 정리 작업 미수행이다. 처리 적합성과 부작용 검사는 분리해야 한다. `all([])`로 참이 되는 ‘검사 대상 없음’을 사용자 화면에서는 작업 성공과 구별한다. 필수 검사 통과만으로 정답을 선언하지 않는다.
