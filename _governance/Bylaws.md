# knowledge-vault 시행령 (Bylaws)

> 헌법([[Constitution]], 2026-07-23 개정판) 아래의 운영 기본값이다. 헌법이
> 무엇과 왜를 정하면, 시행령은 어떻게를 정한다. mechanism 사양은 시행령이 정한
> 행동 범위 안에서 수치와 계산식을 정한다. 사용자 주의나 심의 라우팅에 영향을
> 주는 값의 변경은 브리핑에 보고하며, 사용자는 이를 되돌릴 수 있다. 개정은
> 헌법보다 가볍다 — 사용자 지시 또는 판례 축적(§13)으로 바뀐다. 이 문서의
> 어떤 조항도 헌법을 넘어서지 못한다.
> 2026-07-21 원소별 비준으로 성립하여 구 [[Bylaws-2026-07-06]]을 replaces한다.
> 기초는 에이전트가, 내용의 결정은 사용자가 했다(주도 저작, §1.11).

## §1. 어휘

1. **용어 원칙**: CS·인지과학에서 원어가 통용되는 개념은 원어로, 자연스러운 관용
   한국어가 있으면 한국어로 쓴다. 번역투 조어는 금지한다.
2. **용어 이행 표** — 과거 문서(구 시행령, 결정 기록, 분류 전표)를 읽을 때
   적용한다:

   | 구 문서의 용어 | 현행 용어 |
   |---|---|
   | 스코프, Scope Layer | **Sense**, Sensemaking Layer |
   | Synthesis | **Sense** |
   | 관측 클러스터 | **Scope** |
   | (Knowledge의) 클러스터 | **Domain** |
   | Observation→Sensemaking 증류 | **증류** — Observation 노드로 Sensemaking 노드 형성 |
   | Synthesis 형성 | **응집** — Sensemaking 노드의 조직 |
   | 응집(노드 형성의 뜻으로 쓴 용례) | **증류** |
   | 재배치 | **Sense의 분화 / 구성 Sensemaking 노드의 재배정** |
   | 응고·응고 후보 | **승격 후보** |
   | superseded(표기·상태) | **구판** — 들어오는 replaces에서 컴파일되는 파생 표시 |
   | 권한 근거 | (폐지) — 서명·심의·측정의 기존 제도로 환원 |
   | contradicts 사건 상태(open·resolved·preserved) | (폐지) — 절차는 사건부, 엣지는 존치 판정의 표시 |
   | supports | **supported-by** |
   | 작업대 | Workbench |
   | 술어 엣지 | Predicate Edge |
   | 불변식 | (범주 폐지) → 조문 + §14 검증 제약 |

3. **지칭 규율** — Layer는 인식적 신분, Scope·Sense·Domain은 각 Layer의
   조직 단위, 노드는 개별 기록이다. Layer 전체와 개별 노드를 뭉뚱그리지 않고,
   대상을 각각 Layer·조직 단위·노드로 명시한다.
4. **휴면** — 가시성을 잃되 존재는 유지되는 상태. 망각은 가시성의 박탈이지
   존재의 박탈이 아니다(§11).
5. **재부상(resurfacing)** — 휴면 항목이 다시 가시화되는 것.
6. **채택** — 사용자가 승격 후보를 검토 대상으로 골라 두는 표시. 워크플로우의
   편의 장치이며, 승격이나 서명이 아니다.
7. **승격 후보** — 서로 다른 맥락에서 2회 이상 검색된 Sensemaking 노드.
   브리핑 상단에 부상한다. 맥락의 개체화와 계수는 §11.4를 따른다.
8. **충돌 입건** — 정합성 검사가 충돌 가능성을 사건 후보로 등록하는 절차.
   입건은 모순의 확정이 아니다(헌법 12조 2항).
9. **존치** — 심의가 두 지식의 양립 불가를 인지한 채 둘 다 보존하는 판정.
    contradicts 엣지의 유일한 발생 사유(헌법 10조 3항).
10. **사건부(事件簿)** — 충돌 입건·심의·판정·기각의 절차 기록. 사용자 판정과
    보존할 이력은 파일 정본, 재계산 상태는 엔진 DB(§10.4). 자율권의 판례
    대장과 구별된다.
11. **저자(author)와 기초자(drafter)** — 모든 3-Layer 노드는 frontmatter에
    둘을 함께 표기한다. 저자는 서술의 내용을 결정한 주체, 기초자는 초안을
    생성한 주체다 — 이후의 윤문·교정·국소 수정은 기초자를 바꾸지 않는다.
    사용자가 초안을 지었으면 에이전트가 윤문을 도왔더라도 둘 다
    사용자다(`author: user`, `drafter: user`). 에이전트가 문장을 산출하되
    사용자가 선별·기각·수정 지시의 반복으로 내용을 결정했으면 주도 저작이다
    (`author: user`, `drafter: agent:<하네스>`). 둘 다 에이전트면 에이전트
    저작이다. 단회의 동의·확인은 저자를 바꾸지 않으며 서명으로 기록된다.
    주도가 분명하지 않으면 에이전트 저작으로 표기하고, 사용자는 사후에 상향할
    수 있다. 표기는 사유의 기원이 아니라 행위의 기록이다.
12. **도마(에 오르다)** — 중심부 충돌이 사용자 심의에 소환된 국면(헌법 12조
   4항)을 가리키는 관용 표현.
13. **협업 기록 / 사용자 모델** — 헌법 7조 2항의 두 에이전트 기록.
    구체 파일은 §6.
14. **유효 서명 상태** — 서명 이후 서명 대상 상태가 변경되지 않아 서명이
    유지되는 상태(헌법 9조 2항, §8).
15. **비준 하중** — 양끝이 유효 서명 상태인 supported-by가 기초 의존 위에
    싣는 가중(§9.3·4).
16. **검색의 두 결** — **작업 검색**은 에이전트가 증류·응집·승격 준비를 위해
    재료를 찾는 검색이다. 미서명 강등을 적용하지 않으며, 휴면 시계를 리셋하지
    않는다. **열람 검색**은 사용자의 명시적 검색과 사용자 대면 노출이다.
    미서명 노드는 후보로 표기·강등되고(헌법 11조 3항), 휴면 시계를 리셋한다.

## §2. Knowledge Layer 운영

1. Domain의 신설·분화·병합은 에이전트가 제안하고 사용자가 명명·실행한다(헌법
   3조 3항). 제안은 브리핑에 실린다.
2. Knowledge 노드의 Domain 배치와 임시 제목은 에이전트가 자율로 정하되,
   사용자는 사후 수정권을 가진다.
3. Knowledge Layer에는 사용자에 관한 서명 지식을 조직하는 Domain을 둔다.
   그 명칭은 사용자가 정한다. 이 Domain에는 서명된 Knowledge 노드만 배치하며,
   Observation Layer의 사용자 모델은 그 내용을 복제하지 않고 참조한다.

## §3. Sensemaking Layer 운영

1. 작업 중 집계된 이해가 필요할 때 에이전트는 관련 Observation 노드를 읽고
   Sensemaking 노드를 증류하거나 갱신하며, 이를 하나의 질문이나 의미를 중심으로
   Sense에 응집한다. 기존 Knowledge 노드는 필요에 따라 참조할 수 있다.
   엔진은 의미와 Scope의 locality 신호를 바탕으로 Sense의 조직 후보를
   제안한다. Sense의 분화와 구성 Sensemaking 노드의 재배정은 헌법 4조 3항에
   따라 자동화가 기본이다. Sense의 신설과 임시 명명도 같은 자동화 아래 두며,
   사용자는 사후 수정권을 가진다. 병합은 에이전트가 제안하고 사용자가 실행한다.
2. 자동 분화·재배정은 브리핑에 보고된다. 사용자는 어느 재편이든 되돌리거나
   Sense를 **고정(pin)**할 수 있다 — 고정된 Sense는 자동 분화·재배정에서
   제외된다.
3. Sense의 검색·브리핑 가시성은 마지막 관측·검색 이후 **3개월**에 걸쳐
   점진적으로 낮아진다. 3개월 동안 활동이 없으면 휴면하여 가시성이 크게
   강등된다. 그 Sense에 속한 Sensemaking 노드는 서명 여부와 무관하게 함께
   강등되되, 같은 Sense 안에서는 서명 노드가 미서명 노드보다 높은 검색
   우선순위를 유지한다. 구체 우선순위 계수는 mechanism이 정한다. 새 관측과
   열람 검색은 경과 시간을 초기화하며(§1.16), 재부상은 §11을 따른다.

## §4. Observation Layer 운영

1. **작성 원칙**: Observation 노드는 출처 기반의 추론·사실 기록이다(헌법 5조 1항).
   추론을 기록할 때에는 그것이 추론임을 함께 밝힌다. 세션 로그,
   활동 산출물, 외부 자료는 생성되었다는 이유만으로 편입하지 않는다. 사용자는
   별도의 인입 절차를 수행하지 않는다.
2. **작성 시점**: 작업 밖에서도 재사용할 사실, 감사·재현에 필요한 근거, 이후의
   판단을 바꿀 수 있는 관측을 보고한다. 보고 작성 여부의 검토는 작업 절차지만,
   노드 생성량은 목표나 할당량이 아니다.
3. **기록 형식**:
   - 현행 사실을 나타내는 Observation 노드는 대상·속성·맥락별 정본 한 벌을
     두고, 새로운 관측·확인 또는 권위 있는 지정에 따라 갱신한다. 근거와 마지막
     갱신·확인 시점을 남기며, 충돌은 미결로 표시한다.
   - 감사·재현에 필요한 Observation 노드나 원자료는 특정 시점의 발췌나
     스냅샷으로 고정한다. 고정된 기록은 수정하지 않고, 오류는 원 기록을 가리키는
     정정 기록으로 밝힌다.
4. Observation 노드는 관측이 발생한 활동·출처의 Scope에 배속되며, locality
   신호(주제·활동·시간·출처)를 메타데이터로 보존한다.
5. 상위 Layer의 노드가 갱신 가능한 현행 정본의 특정 상태를 근거로 삼을 때에는
   참조 시점의 스냅샷을 고정한다. 스냅샷 고정은 해당 상태를 정확히 커밋한 뒤
   이루어진다. 정확한 상태를 포함하는 커밋이 없으면 엔진이 먼저 커밋을 생성하며,
   고정이 끝나기 전에는 그 상태를 상위 Layer의 근거로 확정하지 않는다. 스냅샷은
   대상 노드의 식별자와 해당 상태를 포함한 git 커밋 해시로 지정한다. 단순 열람을
   위한 Link는 고정 대상이 아니다.

## §5. Workbench 운영

1. **개설**: 에이전트는 작업 단위로 Workbench를 연다. 개설 시 대응 작업과 근거
   Scope 참조(헌법 6조 2항)를 메타데이터로 선언한다. 작업 중 근거가 확장되면
   참조 선언을 갱신한다.
2. **저자 표기**: Workbench는 작업 공간 전체에 적용되는 저자 표기를 둘 수
   있다(기본값 `author: agent:<하네스>`, `drafter: agent:<하네스>`). 공간 표기가 있으면 개별 서술의 표기는
   생략할 수 있되, **사용자 저작과 외부 인용은 언제나 별도로 표시한다.** 이관 시
   저자·출처 표기를 보존한다.
3. **저자·Scope 식별 형식**: frontmatter의 `author:`와 `drafter:` 필드는 각각
   `user` 또는 `agent:<하네스>`(예: `agent:claude`)로 함께 적고(§1.11),
   `scopes:`에 하나 이상의 근거 Scope를 목록으로 함께 둔다(헌법 6조 2항).
   시스템은 에이전트의 작업 연속성을 세션이 아니라 Scope 단위로 식별한다.
   혼합 문서의 부분 표기는 인용 블록에 출처를 붙이는 방식으로 한다.
4. **조회 범위**: Workbench는 대응 작업의 맥락에서만 로드된다(헌법 6조 3항).
   교차 열람(다른 작업의 Workbench 열람)은 기본 차단이며, 사용자 지시로만
   허용된다. 열람으로 가져온 내용은 근거로 인용할 수 없고, 자기 Workbench가
   선언·갱신한 근거(Scope의 관측, Sense, Knowledge 노드)에서 재도출한다(§5.1).
5. **종료와 이관 검토**: Workbench를 종료하거나 보존 상태로 전환할 때 에이전트는
   작업 밖에서도 필요한 내용을 검토한다. 사실 보고는 Observation 노드로,
   형성된 이해는 Sensemaking 노드로, 세션과 기기를 잇는 맥락은 에이전트 기록으로
   이관한다. 이 검토는 의무 단계지만 노드 생성을 강제하지 않는다. 활성 집합
   이탈로 자동 전환되는 경우의 검토 시점은 §5.6이 정한다. 나머지는
   Workbench 안에서 보존하거나 위생 규칙에 따라 정리한다. 종료 자체는
   Observation 노드를 생성하거나 Workbench 스냅샷을 만들지 않는다.
6. **보존과 재개**: 명시적으로 종료된 Workbench는 보존 상태로 전환한다. 그 밖의
   활성 집합은 최근 1개월 안에 활동한 Workbench와 최근 활동한 Workbench
   30개(가변 기본값)의 합집합이며, 이 집합에서 벗어나면 보존 상태로 전환한다.
   보존은 Workbench 안에서 제자리로 이루어지고, 재개는 그 Workbench를 다시 여는
   방식으로 한다. 활성 집합 이탈로 자동 전환된 Workbench는 §5.5의 이관 검토
   없이 전환되고, 브리핑의 Workbench 현황에 이관 검토 미수행으로 표기된다. 그
   검토는 같은 Scope에서 활동하는 다음 에이전트 세션이나 사용자 지시로 수행하며,
   재개 시에는 재개한 에이전트가 수행한다. 이 표기는 **사용자에게** 처리 의무를
   만들지 않으며(§12.2), 에이전트는 다음 적격 세션에서 이관 검토를 수행한다.
   열린·보존 전환된 Workbench 현황은 브리핑에 실린다.

## §6. 에이전트 기록 운영

1. **파일 지정**: 에이전트 기록 Scope는 Observation Layer의 전용 디렉토리이며,
   다음을 담는다 —
   - **사용자 모델**: `user.md` 한 벌(정본, 헌법 7조 4항).
   - **협업 기록**: `MEMORY.md`(인덱스) + 주제 파일들.
2. **편집 이력**: 에이전트 기록의 변경 이력은 git 커밋으로 남긴다. 이 이력은
   평상시의 갱신을 막지 않으며, 3-Layer 노드가 특정 상태를 근거로 삼을 때
   6항의 고정 지점으로 사용한다.
3. **정본과 포인터**: 다른 프로젝트의 에이전트 기억은 사용자에 관한 내용을
   복제하지 않고 `user.md`를 가리키는 포인터 + 프로젝트 고유 함의만 갖는다.
4. **대조 스캔**: 주 1회(브리핑 생성 시), `user.md`의 주장을 사용자에 관한
   서명된 Knowledge 노드와 대조한다. 충돌 발견 시 서명된 Knowledge 노드가
   우선하며(헌법 7조 6항), 수정 제안이 브리핑에 실린다.
5. **하네스 연동**: 에이전트 하네스는 고정 경로에서 기억을 읽으므로 vault 내
   정본과의 연결이 필요하다. 연결 방식(심링크·미러링 등)은 주 사용 하네스의
   실제 제약과 drift 가능성을 실측한 뒤 mechanism 사양에서 정한다.
6. 3-Layer 노드가 에이전트 기록을 근거로 삼을 때 가리키는 "참조 시점의
   스냅샷"(헌법 7조 7항)은 §4.5와 같이 대상 기록의 식별자와 해당 상태를 포함한
   git 커밋 해시로 지정한다.

## §7. 증류와 승격 워크플로우

1. **증류와 응집**: 에이전트는 하나 이상의 Observation 노드를 발췌·재서술하여
   Sensemaking 노드를 증류하거나 갱신하고, 이를 하나의 질문이나 의미를 중심으로
   Sense에 응집한다. 기존 Knowledge 노드는 필요에 따라 참조할 수 있다.
   **신규 증류의 조성 기본값은 발췌 + 인덱스 + 배선 후보다.** 성숙 과정의
   수정(헌법 4조 4항)에서는 저자 표기 아래 종합 서술이 허용된다. 근거가 된
   Observation 노드는 Observation Layer에 남고, Sensemaking 노드가 이를 Link한다
   (헌법 8조 2항). 발췌는 근거 Observation 노드가 고정 기록이면 그 기록을
   가리키고, 현행 정본이면 §4.5의 스냅샷을 가리킨다. 발췌 자체를 출처와 독립된
   현행 정본으로 갱신하지 않는다. Sensemaking 노드는 출처를 열지 않고도 주장과
   근거 관계를 파악할 수 있을 만큼 자기완결적으로 쓴다. 주요 Link의 쓰임은
   문맥에서 드러나야 하며, 인덱스 목적의 노드는 Link 목록을 허용한다.
2. **Workbench → Layer 이관**: 헌법 6조 5항. 이관된 노드는 저자 표기를 보존하고
   각 Layer가 요구하는 출처를 갖춘 미서명 노드로서 편입 규칙을 따른다. 이관을
   수행한 Workbench가 이관된 노드를 Link하여 작업 맥락과 작업물의 대응을 남긴다.
   이관된 3-Layer 노드는 Workbench를 참조하지 않는다.
3. **Sensemaking 노드 → Knowledge Layer**: 승격은 서명과 독립된 Layer 이동이며,
   §8.1과 같은 선확정 형태로 판정 한 번에 완결한다.
   1. 사용자가 후보를 채택한다(브리핑에서 또는 직접).
   2. 엔진이 판별 3문의 결과, 충돌 후보, 그리고 승격 후의 최종 상태(목표
      Domain·배선 초안 반영)와 그 diff를 제시한다.
   3. 사용자가 승격·목표 Domain·배선을 한 번에 판정한다. 배선이 서명 노드의
      서명 대상 상태를 바꾸는 경우, 이 판정은 제시된 최종 상태에 대한 §8.1의
      서명 동작을 겸하며, 그 write set은 (2)에서 제시된 diff에 열거된 각 서명
      노드로 한정한다 — 같은 내용을 diff로 다시 묻지 않는다.
   4. 에이전트가 같은 노드를 사본 없이 이동하고 승인된 배선·정리를 적용한다.
      서명이 걸린 최종 상태는 엔진이 §8.1(4)대로 해시를 확정한다.
   5. 서명 상태는 Layer 이동과 독립이다 — 미서명 노드는 승격 뒤에도 미서명이고,
      봉인 경계의 상태가 변하지 않으면 기존 서명이 유지된다(§8.3).
   6. 사용자 모델에서 옮겨온 사용자에 관한 주장은 서명 전에는 Sensemaking
      Layer에 머문다(헌법 7조 5항).

## §8. 서명 구현

1. **독립 절차**: 서명은 어느 3-Layer 노드에서든 별도로 이루어질 수 있으며
   승격과 결합하지 않는다. 사용자가 확인하는 상태와 봉인되는 최종 상태가
   어긋나지 않도록 최종 상태를 서명 이전에 확정한다. 구현은 다음 트랜잭션을
   따른다:

   (1) 사용자가 서명할 노드를 고른다.

   (2) 엔진이 정합성 검사를 돌리고(헌법 12조 1항, 충돌 가능성은 입건한다),
   승인 대기 중인 배선과 사전 고지된 의미 비변경 정규화를 반영한 **최종 서명
   후보 상태**와 그 정확한 diff를 제시한다. 충돌 후보와 배선 후보를 함께
   제시하며, 채택되지 않은 배선 제안은 후보로 남는다.

   (3) 사용자가 제시된 최종 상태를 직접 확인하고 서명 동작을 실행한다. 이 행위는
   트랜잭션을 개시하며, 에이전트는 노드 frontmatter의 서명 블록을 대기 상태로
   기록한다. 서명 시점과 선택적 사유를 함께 기록할 수 있고, 지시 원문은 요구하지
   않는다. 이 확인이 승인하는 상태(write set)는 제시된 최종 상태다.

   (4) 엔진이 그 상태를 더 변경하지 않고 최종 상태를 해싱하여, 서명 블록에 상태
   해시·확정 시점·유효 상태를 기록하고 서명과 파일 상태를 함께 확정한다. 확정
   대상이 (3)에서 확인된 상태(write set)와 사전 고지된 의미 비변경 정규화의
   범위를 벗어나면 확정을 중단하고 (2)로 돌아간다. 이 트랜잭션은 해시 확정 뒤에
   서명 대상 상태를 변경하지 않는다.

   노드가 선언하는 Predicate Edge는 서명 대상 상태의 일부다. 효력의 양상은
   헌법 10조 4항을 따른다.

   노드 frontmatter의 서명 블록이 서명 기록의 정본이다. 엔진 DB는 이를 파생
   인덱스로 컴파일하며, DB가 소실되어도 파일의 서명 기록으로 재구성한다. 신규·변경
   서명은 브리핑에 보고한다.
2. **해시 대상**: 서명 대상 상태는 노드의 주장·의미 범위·근거·선언 관계·저작을
   결정하는 내용으로 이루어지고, 검색 인덱스·캐시·측정값·표시용 메타데이터처럼
   그로부터 재생성되는 파생 정보는 제외한다. 최소 포함은 제목 + 본문 전문 +
   노드가 선언하는 Predicate Edge + 저자·기초자 표기이며, 서명 블록과 엔진이
   자동 기입하는 메타데이터는 제외한다. 근거·출처·고정 스냅샷 식별자(§4.5)처럼
   주장의 정당화를 결정하는 frontmatter 필드의 해시 포함 여부는 그 필드들의
   물리 위치와 함께 mechanism 사양이 정한다.
3. **봉인 경계** *(Link/Predicate Edge 분리의 귀결)*:
   - **깨는 것**: 본문 수정(본문 Link의 추가·삭제 포함 — Link는 본문의 일부다),
     그 노드가 선언한 Predicate Edge의 추가·삭제·변경, 그 밖의 서명 대상 상태
     변경.
   - **깨지 않는 것**: 다른 노드에서 들어오는 Link·Predicate Edge, 측정값의
     변동(중심성·엣지 효력 양상), 엔진의 자동 메타데이터, 노드의 Domain·Sense
     소속 변경 및 승격만으로 생기는 포함 위상의 변경.
   - 소속 변경이나 승격 과정에서 서명 대상 상태가 변경되면 봉인을 깬다.
     서명 노드의 소속 변경은 브리핑에 보고된다.
4. 서명이 풀린 노드는 diff 확인 대기로 브리핑에 오른다. 재서명 전까지 미서명
   신분이다(헌법 9조 2항).

## §9. Link와 Predicate Edge 구현

1. **선언과 시야**: Predicate Edge는 선언 노드의 frontmatter에 선언하며 서명
   대상 상태의 일부다. 에이전트는 미서명 노드와 초안에 자유로이 선언할 수
   있다 — 의미는 선언 시부터 유효하다(헌법 10조 4항). 단, contradicts는
   심의의 존치 판정에서만 배선된다(헌법 10조 3항, §10.4). **대칭 술어인
   contradicts는 양쪽 노드가 서로를 배선하는 방식으로 선언한다** — 한쪽에만
   선언하지 않는다. 이로써 두 방향 모두 참조가 성립하여 재검토 전파가 자연히
   대칭이 된다(헌법 10조 6항, 11조 4항). 역방향 시야는 엔진이 컴파일한다
   (Backlink 방식). 물리 스키마(YAML 형식)는 mechanism 사양에서 정한다.
2. **Link 컴파일**: 본문 Link는 기본 의존(중심성의 약한 기본 가중)으로 컴파일한다.
   의존의 산입과 술어별 중심성 가중은 §9.4를 따른다 — 같은 쌍에 본문 Link와
   Predicate Edge가 병존해도 의존은 1회만 산입한다(이중 계상 방지). Workbench의
   참조는 전부 비산입한다(헌법 6조).
3. **효력과 전파**: supported-by의 비준 하중은 양끝이 유효 서명 상태일 때
   §9.4의 가중으로 실리고, 그 외에는 기초 의존으로만 계상한다(헌법 11조 3항).
   서명된 구판에 대한 replaces의 검색 강등은 선언 노드의 유효한 서명을
   요구하고, 미서명 구판에는 이 요건을 적용하지 않는다(헌법 10조 4항).
   **전파**(헌법 11조 4항): 참조 대상 노드가 새로운 상태로 재서명되면 그
   노드를 참조하는 노드에 재검토가 전파된다 — 본문 Link는 재검토 대기로 브리핑에
   오르고, Predicate Edge는 그 효력이 정지한 채 브리핑에 오른다. 전파는 봉인을
   깨지 않는다(§8.3) — 전파받은 노드의 서명은 유지되며, 재검토 후 재서명하면
   효력이 회복된다(선언 내용이 변하지 않았다면 diff 없는 확인). 참조하는 쪽의
   재서명은 참조 대상으로 전파되지 않는다. 어느 한쪽의 서명이 풀린 동안에는 서명에
   결부된 효력이 정지하고, 같은 상태로 복귀하면 회복한다. 전파 범위의 임계와 구체
   계수는 mechanism이 정한다.
4. **중심성 컴파일 — 산입의 정본 규칙**: 인덱싱 시 계산하며, 의존의 산입은 이 항이
   단일 정본으로 정한다. 다른 조항은 이 항을 참조한다. 술어는 종류에 따라 구별된
   중심성 양상을 가지며, 모두를 같은 의존으로 환원하지 않는다 (헌법 10조 4항).
   - **기초 의존(본문 Link)**: 본문 Link는 방향을 가진 쌍 단위로 1회 산입하며
     중심성의 약한 기본 가중으로 작용한다. 같은 쌍의 같은 방향에 Link와
     Predicate Edge가 병존해도 기초 의존은 1회다(이중 계상 방지).
   - **supported-by**: 기초 의존 위에 강한 가중을 싣는다. 양끝이 유효 서명
     상태이면 비준 하중으로, 그 외에는 기초 의존과 같은 압력으로 계상한다.
   - **replaces**: 의존 가중을 더하지 않는다. 대신 강등이 발화하는 동안 구판을
     가리키는 의존을 신판의 개정 비용으로 **승계**한다 — 구판의 중심성으로는
     계상하지 않으며, 배선 이관(§9.5)이 끝나면 승계는 물리적 참조로 실현되어
     해소된다. 구판의 주장 자체에 의존하여 구판을 계속 가리키는 Link는
     승계에서 제외한다.
   - **contradicts**: 의존이 아니므로 중심성에 산입하지 않는다(가중 0). 양쪽
     선언(§9.1)으로 재검토 전파는 대칭으로 일어나며, 심의 소환 범위(헌법 12조
     4항)에 작용하여 당사자와 그 의존 이웃을 함께 부른다.
   - **미서명·휴면**: 미서명 노드는 자신을 위한 중심성이나 supported-by 하중을
     갖지 않지만, 미서명 노드에서 서명 노드로 향하는 기초 의존은 참조 대상 서명
     노드의 재검토 비용에 포함한다. 휴면 노드의 의존도 산입에서 제외되지
     않는다 — 휴면은 가시성의 박탈이지 의존의 소멸이 아니다.
   - **배제와 위임**: Workbench의 참조는 배제한다(헌법 6조, 11조 3항). 중심성은
     Sense의 응집 기준으로 사용하지 않으며, 구체 가중치·승계 계수·계산식은
     mechanism이 정한다.
5. **개정 계보**: 현재 내용을 제자리에서 바꾸어도 기존 Link가 새 내용을
   정직하게 가리키면 정련으로 보고, 같은 노드를 수정한 뒤 재서명한다. 그렇지
   않으면 새 노드를 만들고 replaces를 선언한다. 구판의 열람 표시와 검색 강등은
   들어오는 replaces에서 컴파일하며, 강등의 효력 조건은 §9.3을 따른다. 미서명
   구판이 강등될 때 그 구판의 author가 user이면 — 사용자 행위 없이 이뤄진
   강등이므로 — 이 사건을 브리핑에 알림으로 올린다(§12.1). 옛 노드는 수정하지
   않는다. 서명된 replaces가 성립하면 구판을
   가리키던 기존 Link의 이관을 주기적으로 검토한다 — 에이전트가 이관 후보를
   검토해 브리핑에 올리고, 사용자의 일괄 승인에 따라 엔진이 재서명을 전파한다.
   이 일괄 승인은 열거된 각 노드에 대한 §8.1의 서명 동작으로 보며, 그 write
   set은 브리핑에 제시된 이관 diff 목록으로 한정한다(§14.9). 구판의 주장 자체에
   의존하는 Link는 구판을 계속 가리킨다.

## §10. 정합성 검사 구현

1. 구성은 hybrid다: 임베딩 유사도 + Predicate Edge 그래프 + LLM 판정. **LLM
   판정은 recommend-only, no veto** — 검사기도 착각한다.
2. 주기 스캔은 주 1회. 스캔 대상은 유효 서명 노드 사이의 충돌이다. 발견 결과는
   충돌 후보로 입건하여 브리핑에 올리고, 이 단계에서는 Predicate Edge를 변경하지
   않는다. 미서명 노드의 충돌은 서명 시 검사에서만 본다. 서명 시 검사에서
   발견된 충돌의 중심부/주변부 라우팅(헌법 12조 4항)은 충돌 상대방인 기존
   노드의 개정 비용을 기준으로 한다 — 서명 대상 노드는 아직 자신의 중심성을
   갖지 않는다. 휴면 항목은 스캔 가시권에 있다.
   주기 스캔은 신규·갱신된 Observation 노드와 서명 노드 사이의 근접·모순
   가능성 검사도 포함한다. Observation 노드는 Predicate Edge의 당사자가 될 수
   없으므로 이 결과는 관측 영향 검토 후보로 등재하고 브리핑에 올린다. 관측 영향
   검토 후보는 충돌 입건의 대상이 아니다.
3. **판정 기준** — 충돌 후보는 검사기가 입건하는 절차상 지위이고, 모순은 사용자
   심의의 판정이다:
   - **모순** = 사용자가 보유한 두 지식이 동시에 참일 수 없음.
     시험: "둘 다 참일 수 있는가?"
   - **supported-by** 시험: "근거 노드가 뒤집히면 이 노드의 근거가 흔들리는가?"
     (= 개정 비용의 국소 단위)
   - **replaces** 시험: "기존 노드를 제자리에서 바꾸어도 그 노드를 가리키던
     Link가 새 내용을 정직하게 가리키는가?" 아니오라면 새 노드를 만들고 교체
     판단에서 replaces를 컴파일한다.
   - **기각 4종**(모순 아님): **대항**(상대항이 보유 지식이 아니라 보고·인용된
     타인의 입장 — "주장 A와 달리 나는~"), **별개**(닮았으나 다른 물음),
     **중복**(같은 주장 두 벌 — 처방은 심의가 아니라 하나로 정리), **관점차**
     (같은 대상, 다른 좌표 — 각자의 틀 안에서 양립).
4. **사건 생애**: 감지·입건(사건부 등재) → 브리핑 → 사용자 심의. 출구는 셋 —
   **개정**(한쪽을 정련 또는 교체로 고친다. 교체면 replaces 계보가 생긴다),
   **존치**(양립 불가를 인지한 채 둘 다 보존한다. 양쪽 노드에 서로를 가리키는
   contradicts를 배선하며(§9.1), 각 선언 노드의 재서명과 함께 기록된다),
   **기각**(모순 아님 — 기각 4종).
   기각은 상태가 아니라 퇴장이다. 입건·계류·판정·기각의 절차 기록은 노드가
   아니라 사건부에 남긴다. 사건부의 사용자 판정과 보존할 이력은 vault 내 파일
   정본으로 두며, 포맷은 소송 절차가 확립될 때까지 draft로 유지한다(유실 방지
   우선). 재계산 가능한 상태는 엔진 DB에 두고, DB가 소실되어도 정본에서
   재구성한다.
5. **기판력과 그 한계**: 판정이 끝난 사건은 같은 당사자 상태·같은 충돌 사유·
   실질적으로 같은 증거 집합에 대해 재소송되지 않는다. 사건의 동일성은 당사자의
   서명 상태뿐 아니라 충돌 사유와 증거 집합으로 결정된다. 따라서 새로운
   Observation이 추가되거나 기존 판정의 전제가 무너지면 — 당사자 상태가
   그대로여도 — 새 사건으로 입건할 수 있다. 기판력은 무의미한 재소송을 막을 뿐
   오류를 영구 고정하지 않는다.
6. 라우팅 임계(중심부/주변부)는 중심성 분포에 따라 엔진이 보정한다. 이 자동
   보정의 위임은 판례 대장에 한 번 기록한다. 개별 보정값과 변경 이력은 엔진 운영
   기록에 남기고, 변경은 브리핑에 보고하며, 사용자는 어느 보정이든 되돌릴 수 있다.

## §11. 망각과 주의

1. **원칙: 전부 수집하지 않으며, 사용자의 주의를 요구하는 표면은 유한하다.**
   Observation Layer에는 재사용·감사·판단 근거의 가치가 있는 사실 보고만 두고,
   이미 3-Layer에 편입된 노드는 아래 규칙에 따라 가시성을 조절한다. Sense
   단위의 강등·휴면은 §3.3이 정한다.
2. 미서명 Knowledge 노드는 생성 또는 마지막 열람 검색으로부터 **한 달**간 주의
   표면(브리핑·활성 목록)에 머물고, 그 후 휴면한다. 열람 검색의 히트만 시계를
   리셋한다(§1.16).
3. 차등: 사용자가 직접 쓴 미서명 메모는 휴면하지 않는다 — 직접 쓴 것은 그
   자체로 주목의 산물이다. 쌓여서 어지러우면 사용자 지시로 "느린 휴면"으로
   조정할 수 있다.
4. 재부상의 세 경로: ①새 노드·활동이 휴면 항목과 의미적으로 닮으면 자동 부상
   ②정합성 검사는 휴면을 본다 ③사용자의 명시 검색. 재사용 맥락은 Workbench
   안에서는 Workbench 단위로, Workbench 밖에서는 명시적 사용자 작업 단위로
   개체화한다. 같은 맥락 안의 반복 검색은 노드당 1회만 센다. 휴면 Sensemaking
   노드가 새 맥락에서 실제로 검색되어 재부상하면 승격 후보의 재사용 횟수에
   포함하고, 자동 추천이나 브리핑 노출만으로는 포함하지 않는다.
5. Knowledge Layer의 서명 노드는 망각되지 않는다. 같은 지식의 정련은 제자리
   수정과 재서명으로, 기존 참조의 의미가 달라지는 교체는 새 노드와 replaces
   계보로 처리한다(§9.5).
6. 시스템은 3-Layer에 편입된 노드를 스스로 영구 삭제하지 않는다. 영구 삭제는
   사용자의 직접 행위로만 가능하다. Workbench의 미이관 임시물은 §5의 위생 규칙을
   따른다.

## §12. 주간 브리핑

1. 데몬이 주 1회 생성한다. 구성: 승격 후보 / 신규 미서명 노드 / 신규·변경 서명 /
   diff 확인 대기(서명 풀림) / 전파된 재검토 대기(§9.3) / 서명 노드 소속
   변경(§8.3) / 효력 상실
   Predicate Edge / 사용자 저작 구판의 강등 알림(§9.5) / 구판 배선 이관 후보 /
   충돌 후보 / 열린 충돌 사건 / 관측 영향 검토 후보 / 재부상 항목 /
   Sense 분화·재배정 보고 및 병합 제안 / Domain 분화 제안 /
   사용자 모델 대조 결과(§6.4) / Workbench 현황(§5.6) / 임계·보정값 변경
   보고(§10.6) / 검증 실패 보고(§14) / Review Trigger 점검.
2. **읽기는 선택이다.** 처리 의무는 없다 — 죄책감 큐를 만들지 않는다. 안 읽어도
   시스템은 돌아간다.
3. **Review Trigger** — Observation 노드의 수나 작성 빈도는 성과 지표로 삼지
   않는다. 다음 현상이 반복되면 구조 재심을 알린다:
   - 필요한 사실 보고가 없어 같은 작업 맥락이나 사실을 반복해서 재구성한다.
   - 근거로 삼은 Observation 노드 또는 Knowledge 노드를 추적할 수 없는
     Sensemaking 노드가 쌓인다.
   - 승격 후보의 장기 정체가 현재 작업을 방해한다.
   - 미서명 노드의 참조가 중심성 분포나 심의 소환 범위를 왜곡한다.
   - Sense 분화가 병합을 지속적으로 앞질러 파편화가 누적된다.

## §13. 권한 차등과 판례 대장

1. 결정 층위별 권한(헌법 13조 2·3항의 시행):

   | 층위 | 예 | 권한 |
   |---|---|---|
   | 헌법적 | 층 구조, 술어, 서명·승격 규칙 | 원소별 비준 |
   | 중간 | Domain 신설·명명 | 에이전트 제안 → 사용자 명명·실행 |
   | 운영 | 노드 배치, 임시 제목, Sense 신설·분화·재배정, Workbench 내부 | 에이전트 자율 + 사용자 사후 수정권 |

2. 모호하면 승인제가 기본값이다(헌법 13조 3항).
3. **판례 대장** — 자율권 확대는 여기 기록된 것만 유효하다. 회수 가능하다.
   서명의 판단은 판례에 따라 위임되지 않는다. 사용자의 명시적 서명 행위를 기록하고
   확정하는 절차는 §8.1을 따른다.

   | 날짜 | 부여된 자율권 | 근거 |
   |---|---|---|
   | 2026-07-07 | Sense(당시 스코프)의 재배치·재배정·분화 자동화 | 헌법 4조 3항 (창립 비준) |
   | 2026-07-20 | 라우팅 임계 자동 보정 | §10.6 |
   | 2026-07-22 | Sense의 신설·임시 명명 자동화 | 헌법 4조 3항, §3.1 |

   위 기록의 `재배치`는 창립 당시의 표현이다. 현행 용어에서는 Sense의 분화와
   구성 Sensemaking 노드의 재배정으로 구분한다.

## §14. 엔진 상시 검증 제약

이 목록은 헌법과 시행령 조문의 집행 항목이며 독자적 권위가 없다. 엔진이 상시
검증하고, 위반은 브리핑에 보고된다.

1. 서명 기록은 사용자의 명시적 서명 행위를 근거로만 생성하며, 에이전트는 그
   행위를 추정하지 않는다. 서명 블록의 확정은 엔진만 수행한다. (헌법 9조 3항,
   §8.1)
2. 미서명 노드: 자신을 위한 중심성·supported-by 하중 없음, 검색 후보
   표기·강등. 미서명 노드의 Link·Predicate Edge가 서명 노드에 만드는 의존은
   §9.4의 정본 규칙에 따라 참조 대상의 개정 비용에 포함한다. 서명된 구판에 대한 replaces의 강등 효력은
   선언 노드의 유효한 서명을 요구하며, 미서명 구판에는 이 요건을 적용하지
   않는다. (헌법 10조 4항, 11조 3항, §9.3·4)
3. Workbench: 전역 질의 제외, Predicate Edge 없음, 참조 비산입,
   3-Layer 노드와 에이전트 기록의 Workbench 참조 없음. 이관 시 Workbench에서
   이관된 노드로 향하는 Link 유지. (헌법 6조 3·4항, 7조 7항, §7.2)
4. 에이전트의 3-Layer 쓰기는 엔진을 경유한다. 엔진은 쓰기 경로를 기록한다.
   무표기 서술은 기록 경로가 아는 것으로 보충한다 — 엔진 경유 쓰기는 경로
   기록의 하네스를 기초자로 보충하고 저자는 `unknown`으로 두며, 표기 의무
   위반으로 보고한다. 경로 기록이 없는 직접 기입은 `author: unknown`,
   `drafter: unknown`으로 보충하고 브리핑에 올린다. 사용자는 자신의 저작을
   사후에 상향할 수 있다(§1.11). 에이전트의 직접 파일 쓰기는 Workbench에
   한한다. (헌법 9조 4항, 13조 4항)
5. 같은 정보의 살아있는 사본 감지(중복 금지). (헌법 8조 2항)
6. Observation 노드의 보존 형식 검증 — 현행 정본의 중복, 고정 기록의 제자리
   수정, 갱신 가능한 정본을 특정 상태로 고정하지 않은 근거 참조를 감지한다.
   (헌법 5조 3항, 7조 7항, §4.3·5)
7. 시스템 발의 영구 삭제 없음. (§11.6)
8. 서명 블록의 대기→확정 전이와 상태 해시를 검증한다. 노드가 선언하는
   Predicate Edge는 상태 해시에 포함하고, 서명 블록과 엔진 자동 기입
   메타데이터는 제외한다. 해시 불일치나 잘못된 전이는 미서명으로 처리하고
   브리핑에 보고한다. (§8.1·2)
9. 서명 트랜잭션의 실제 변경이 승인된 write set과 사전 고지된 의미 비변경
   정규화의 합집합 안에 있는지 검증한다. (§8.1)
10. contradicts Predicate Edge는 사건부의 존치 판정과 대응해야 하며, 양쪽 노드에
    서로를 가리키는 짝으로 선언되어야 한다(§9.1). 대응 없는 contradicts, 짝이
    없는 한쪽 선언, 상태 필드를 가진 contradicts, 서명된 구판을 서명 없는
    선언 노드에서 강등한 replaces는 위반으로 보고한다. (헌법 10조 3·4항, §10.4)
