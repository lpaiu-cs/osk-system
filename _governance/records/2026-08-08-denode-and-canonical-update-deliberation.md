# 2026-08-08 — 통치 문서 비노드화와 정본-갱신 체계 심의

> 통치 사료 — 규범이 아니라 그 규범이 어떻게 정해졌는지의 기록.

## 물음

엔진·통치 문서의 저작을 정본 저장소에서 먼저 하고 각 인스턴스가 그것을
받아 오게 하려면, 갱신 기제를 어떻게 설계하는가. 인스턴스의 백엔드는
알 수 없다(git 데몬·Supabase·로컬 전용).

## 경위

독립 설계 3편을 병렬로 받았다(설계자: opus-4.8 · fable-5 · opus 계열
1편). 셋은 서로 모르는 채 같은 결론에 독립 도달했다 — 정본 상류 승격,
갱신은 발행의 역방향, 해시 키 서명의 자동 미서명 활용, 출처 추상화,
fail-closed. 갈린 곳은 소유 분류(2분/3분), 통치 병합(사이드카/3-way/회피
설계), 릴리스 증빙, 신규 설치 통일이었다.

## 사용자 결정 (2026-08-08)

1. **통치 문서는 노드로 다루지 않는다** — 시스템의 근본이므로 시스템
   내부에 속하지 않는다. 서명의 대상이 아니고, 효력 발생 여부와 무관하며,
   갱신 시 덮어쓴다. (선행 결정 「노드 유지, Space 제외」의 남은 반절을
   걷어낸 것 — 원칙을 물리까지 관철.)
2. **갱신용 별도 매니페스트를 만들지 않는다** — 적용 범위는 릴리스 안의
   발행 매니페스트가 정한다.
3. **통치 병합은 회피 설계** — 정당한 변이는 통치 문구 밖(로컬 설정·대장)
   으로 밀어내고, 드리프트는 덮지 않고 표면화한다.
4. **릴리스 증빙은 비준증빙** — 파일별 내용 해시 목록(`release.json`)을
   사용자의 대화형 선언으로 고정한다.
5. **신규 설치는 버전 0에서의 첫 갱신**으로 통일한다.

## 집행

- 헌법 3조 6항·14조 1~3항, 시행령 §10, Mechanism §1 4항 개정 + 통치 문서·
  사료 8건의 frontmatter 제거 (통치 문서 비노드화)
- Mechanism §1-2(정본과 갱신) 신설 + `osk.release`/`osk.update` 구현
- 서명 대장의 기존 통치 문서 서명 기록은 이력으로 남되 판정 대상에서
  빠진다. 발행의 서명 가드는 폐지되고 릴리스 비준증빙이 그 자리를 잇는다.

## 후속 결정 — 같은 날, 결정 1의 조정

비노드화를 집행해 보니 두 가지가 아팠다: 인스턴스별 수용 기록의 소실(헌법
1조 사용자 주권과의 긴장), 명시 조회(read_node) 도달 상실. 재심의 끝에
사용자가 결정 1을 조정했다:

- **통치 문서는 §1 노드 계약을 따르는 특수한 노드다** — frontmatter 복원,
  검색·중심성 불산입과 표면 쓰기 거부는 유지.
- **서명 복원, 단 의미 재규정** — 서명은 효력의 요건이 아니라 **각 인스턴스
  사용자의 수용 기록**이다. 효력은 정본 배포로 발생한다(결정 4·5 유지).
  갱신이 통치 문서를 덮으면 서명이 자동으로 풀리고, 재서명이 수용이 된다.
- 정본 저장소에는 대장이 없으므로 정본의 비준은 비준증빙, 인스턴스의 수용은
  서명 — 기초자도 자기 인스턴스에서는 여느 사용자처럼 서명한다.
- 결정 2(별도 갱신 매니페스트 없음)·3(병합 회피)·4(비준증빙)·5(버전 0
  설치)와 갱신 기제 구현은 그대로 유효하다.

같은 자리에서 상설 절차 하나가 추가됐다: **헌법(Constitution.md)은
에이전트가 직접 수정하지 않는다** — 조문 diff 초안을 제시하고 적용은
사용자가 한다.
