# 판독의 결속과 관측의 완전성 — v3.7.1

## 적용 시 반드시 할 것

**데몬은 프로세스째 멈춘다. `Stop-ScheduledTask`만으로는 멈추지 않는다.**
예약 작업이 `cmd /c ... pythonw.exe ...` 꼴이라 작업 인스턴스를 끝내도 손자
`pythonw`가 살아남아 싱글턴 잠금을 쥔 채로 남고, 갱신이 fail-closed로 멈춘다
(v3.7.0 적용에서 실제로 걸렸다).

```powershell
Get-CimInstance Win32_Process -Filter "Name LIKE 'python%'" |
  Where-Object { $_.CommandLine -like '*sync_daemon*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

프로세스를 셀 때 **하나를 둘로 세지 않는다.** venv의 `python.exe`/`pythonw.exe`는
베이스 인터프리터를 자식으로 띄우는 **런처 스텁**이라, 데몬 하나가 두 프로세스로
보인다. MCP 서버도 같다.

v3.7.0부터는 판본 관문이 서 있으므로 MCP 서버 재기동을 잊어도 안전하다 —
낡은 프로세스가 자기 다음 쓰기에서 스스로 거부된다.

## 무엇을 고쳤나

독립 검토(gpt-5.6-sol)가 **재현해 보낸** 정확성 결함 둘과, 그것이 드러낸 셋째.
셋 다 다시 재현해 확인했고, 셋 다 v3.7.0의 수트 835/5가 **놓쳤다.**

### 1. 읽지 않은 상태의 해시를 내주었다 (자료 소실)

`read_node`가 본문은 캐시된 노드에서, 해시는 디스크에서 새로 재어 붙였다.
같은 크기로 고치고 mtime을 되돌리면 지문이 같아 racy 창 밖이므로 캐시가
유지되고, 호출자는 **옛 본문 + 새 해시**를 받는다. 그 해시가 다음
`update_node`의 CAS를 통과해 외부 편집을 조용히 지운다.

Mechanism §6-2 4항은 해시를 *"읽은 상태의 증거"*로 규정한다 — 읽지 않은 상태의
증거를 발급하고 있었다. `contract.parse_bytes`를 두어 **바이트를 한 번 읽고 그
바이트에서 본문과 해시를 함께** 만든다. 캐시가 낡아도 다음 쓰기는 CAS에서
안전하게 거부된다.

이 결함은 v3.6.0에도 있었다. v3.7.0이 만든 것이 아니라 드러낸 것이며, racy
가드가 막아 줄 것이라고 암묵적으로 기댄 자리였는데 막지 못한다.

### 2. 순회가 열거 실패를 삼켰다 (조용한 오염)

`_scan`의 `except OSError: continue`. 디렉토리 하나가 안 읽히면 이름 색인이 그
노드를 못 보고 **다른 군집에 같은 이름이 거부 없이 만들어진다** — 재현했다.
`epoch.py`에서 같은 fail-open을 막아 놓고 여기는 남겨 둔 것이 일관성 결여였다.

이제 오류를 위로 올려 `Index.complete`로 들고, 쓰기 표면 넷이 불완전 관측
위에서 거부하며, 읽기 캐시도 그것을 키로 접어 두지 않는다. 유일성은 **전체를
봐야** 말할 수 있다(시행령 §11 — 실패는 보류·보고).

### 3. 파손 파일이 있으면 id 전수 대조가 성립하지 않는다

`_existing_ids`가 판독 실패 노드를 건너뛰었다. 그 파일의 id를 모르면 새 id가
겹치지 않는다고 증명할 수 없다 — Mechanism §2 1항은 *"유일성의 담보는 길이가
아니라 이 검증"*이라고 명시한다. 이제 거부하고 고치라고 말한다.

### 4. 이름→파일 해석의 중복 순회 (성능)

`_live_locate`가 매 `update_node`·`move_node`마다 파일시스템을 다시 훑었다.
그 규율의 근거는 *"mcp_server의 fingerprint 캐시 색인으로 해석하면 낡은 경로에
작용한다"*였는데, 쓰기 통로가 쓰는 것은 그 캐시가 아니라 같은 잠금 안에서 방금
지은 색인이다. 규율의 뜻은 지키고 중복만 없앴다 — 합성 25,000 노드에서
**289 ms → 0.0 ms**.

## 수트에 무엇을 넣었나

예제가 아니라 **불변식**으로 적었다.

- 성공한 `read_node`의 해시는 **반환한 body를 만든 바로 그 바이트**의 해시다.
- 열거 실패가 하나라도 있으면 **쓰기 성공은 0건**이다.
- 판독할 수 없는 노드가 있으면 id 발급을 주장하지 않는다.

수트 857 통과 / 기지 5건. 이 셋을 겨눈 뮤테이션 5종 **전부 검출(5/5)**.

## 규모는 v3.7.2로 연다

v3.7.0의 판정 노드는 관문을 *"5만 노드에서 새 노드 생성이 아프면 그때"*로
적었다. 그 관문을 실제로 재 보니 **틀린 지표를 보고 있었다.**

실 vault의 본문 크기 분포와 치우친 fan-out(군집 하나가 전체의 76%)을 보존한
합성 vault 실측:

| | 5,000 | 25,000 |
|---|---|---|
| 이름 색인 | 66 ms | 382 ms |
| 계약 전수 판독 p50 | 665 ms | 13,188 ms |
| 계약 전수 판독 **p95** | 27,080 ms | **147,850 ms** |
| `create_node` | 722 ms | **4,754 ms** |
| `update_node`(이름) | 139 ms | 674 ms |
| `update_node`(**id 핸들**) | 804 ms | **3,619 ms** |
| **전역 잠금 보유**(create) | — | **3,463 ms** |
| Searcher 메모리/프로세스 | 29 MiB | **150 MiB** |

네 가지가 이 판정을 v3.7.2의 심의 대상으로 만든다.

1. **지연이 아니라 직렬화다.** `create_node`가 25,000에서 전역 잠금을 3.5초
   쥔다. 이 기기에 MCP 서버가 26개 떠 있다 — 한 하네스의 생성이 나머지 전부를
   그만큼 세운다. 지금까지의 모든 수치는 "혼자 쓸 때"였다.
2. **id 핸들이 이름보다 5배 비싸다.** 중복 순회를 없앴는데도 남는다 — id는
   frontmatter 안에 있어 전수 판독을 피할 수 없다. 그리고 쓰기 응답이 id를
   돌려주므로 드문 경로가 아니다.
3. **메모리가 프로세스 수에 곱해진다.** 25,000에서 프로세스당 150 MiB이면
   26개에 3.9 GB다. 캐시가 없는 지금 판에도 적용된다.
4. **p95가 p50의 11배다.** 세 번의 독립 실행에서 재현됐다(141,660 / 168,166 /
   147,850 ms). 첫 접근 꼬리이며 대량 pull·새 기기·복원 직후에 실제로 문다.
   **중앙값으로 규모를 판단하면 틀린다.**

순수 낭비는 이 판에서 다 걷어냈다. 남은 병목 셋은 같은 뿌리에서 나온다 —
id 유일성과 검색이 frontmatter 전수를 요구한다는 것. 그것은 상수를 깎는 일이
아니라 **구조 결정**이므로(공유 파생 색인·변경 증명·잠금 보유시간), v3.7.0
때처럼 독립 심의를 붙여 v3.7.2로 연다. 위 수치가 그 의뢰문의 재료다.
