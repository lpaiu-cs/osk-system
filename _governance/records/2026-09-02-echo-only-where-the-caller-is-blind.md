# 에코는 모르는 자리에만 — v3.9.0

## 정정 — v3.9.0은 절반만 담았다

**이 문서는 두 수정을 서술하지만 v3.9.0에는 하나만 실렸다.** 성공한 쓰기의
전문 제거(10.4%)는 들어갔고, **상한 초과 거부의 전문 제거(6.8%)는 빠졌다.**
아래 「무엇을 고쳤나」의 표에서 *상한 초과 거부* 행은 v3.9.0에 해당하지 않는다.

원인: PR #22가 커밋 하나만 담은 채 23:00:03에 머지됐고, 두 번째 커밋은
23:12:16에 이미 닫힌 브랜치로 갔다. 머지 커밋의 제목이 첫 커밋만 가리켰는데
릴리스 전에 그것을 대조하지 않았다. 릴리스 보고 모드의 변경 파일 목록은 커밋이
하나든 둘이든 같아서 이 누락을 잡지 못한다 — **파일 목록이 아니라 내용을
확인해야 했다.**

빠진 수정은 v3.9.1에 실렸다. 확인법:
`git show <태그>:_governance/_engine/osk/scope_memory.py | grep -c "full=False"`
— **v3.9.0은 1, v3.9.1은 2**다.

v3.9.0 태그가 증빙하는 문서는 이 정정 이전의 원문이다. 증빙은 그 시점의 상태를
고정하는 것이므로 그대로 두고, 트리의 이 문서에 정정을 남긴다.

## 적용 시 반드시 할 것

**응답 계약이 바뀐다.** `scope_memory`의 **성공한 쓰기**와 **상한 초과 거부**에
`text`가 더 이상 실리지 않는다. 그 키를 읽던 코드는 깨진다 — 실제로 회귀 수트의
CLI 검사가 깨졌다. `hash`·`chars`·`limit`·`remaining`·`eviction`은 그대로다.

**수트는 `mcp` 패키지가 있는 파이썬으로 돌려라.** 없는 인터프리터로 돌리면 기지
실패 5건이 **22건**으로 나오고, 그 기준선 위에서는 무엇이 깨졌는지 가릴 수 없다
(이 판을 만들며 실제로 한 번 잘못 잡았다). `osk` 셸 명령은 없다 —
`PYTHONPATH=_governance/_engine python -m osk.release|osk.update`.

## 어떻게 드러났나

표면 예산은 자로 재는데 표면의 **효용**은 서술로만 있었다(#19). 그래서 이 기기의
Claude Code 트랜스크립트를 전수 조사했다 — 14일 창, 982파일 1.5GB, osk 호출
**721건 / 1,484,852토큰**.

트랜스크립트가 요청마다 `usage` 전체를 남기므로 비용은 추정이 아니라 항등식으로
떨어진다: `prompt(n+1) - prompt(n) - output(n)`. 이 값을 결과 문자수 실측과
교차 검증하는 게이트를 세웠고, **게이트가 먼저 FAIL을 냈다.** 계측 함정을 세 번
밟았고(오탐 grep·`message.id` 접기·세션 포크 중복) 게이트가 매번 잡았다. 방법과
함정은 `[[osk 도구 토큰 실측 — 트랜스크립트 계측법과 함정 다섯]]`.

드러난 것:

- **`scope_memory`가 osk 비용의 42.7%**(634,740토큰). 노드 도구가 아니다.
- 그중 **성공한 쓰기 107건의 전문 에코가 154,955토큰(10.4%)**. 호출자가 방금
  보낸 바이트 그대로다.
- **osk 호출 140/721(19.4%)이 실패**한다. `is_error`로는 12건만 보인다 —
  거부는 성공 응답 본문의 `"ok": false`로 온다.
- 상한 초과 거부 87건의 응답을 전수 파싱하니 페이로드 202,520자 중 `text`가
  **127,268자(63%)** = 101,006토큰(6.8%).

## 무엇을 고쳤나

§9-2 5항이 요구하던 **"성공·실패와 무관하게 전문과 잔여"**를 기준 하나로 갈랐다
— **호출자가 저장본을 모르는가.**

| 자리 | 전문 | 왜 |
|---|---|---|
| 읽기 | 싣는다 | 요청한 내용 자체다 |
| 해시 불일치 | 싣는다 | 다른 기기의 통합이 들어왔다(§9-2 8항). 전문 없이는 그 위에서 다시 통합할 수 없다 |
| 해시 누락·착지 오류 | 싣는다 | 호출자가 현재 상태를 안 봤다 |
| **성공한 쓰기** | **뺀다** | 방금 보낸 바이트 그대로다 |
| **상한 초과 거부** | **뺀다** | 디스크를 안 바꿨다. 다듬을 것은 저장본이 아니라 자기 초안이다 |

조항의 목적("보이지 않는 것은 통합되지 않는다")은 두 부분인데 **작동부는 잔여
쪽**이다. 호출자는 글자를 셀 수 없다 — 실측 상한 초과폭의 중앙값이 **49자**,
33%가 25자 이내였다. 그래서 잔여·자수·상한은 전부 남긴다.

`hash`를 남기는 이유는 연쇄다. 실측상 `update_node`의 `expect_hash` **47%**가
직전 쓰기 응답의 해시를 이어 써서 읽기를 아끼고 있다. 거부에서도 해시가 오므로
재시도가 재읽기 없이 이어진다.

"무엇이 들어 있는지"는 **세션 시작 훅이 이미 세션당 한 번 싣는다**
(`claude_session_start.py`). 조항이 요구한 가시성은 거기서 충족된다.

## 시험과 검출률

수트 **935 → 946 통과**, 기지 실패 5건 불변. **뮤테이션 검출 5/5.**

| 뮤턴트 | |
|---|---|
| 성공에 전문 부활 | 검출 |
| 전문을 어디에도 안 실음 | 검출 |
| 해시를 깨뜨림(연쇄 단절) | 검출 |
| 상한 초과에 전문 부활 | 검출 (엔진·CLI 양쪽) |
| 해시 불일치에서 전문 제거 | 검출 |

옛 단언 6곳은 **저장물 되읽기**로 바꿨다. 응답 에코가 아니라 디스크에 남은 것을
보므로 검사가 강해졌다 — 특히 비밀값 필터 검사는 이제 "응답에 안 보인다"가
아니라 "저장본에 없다"를 확인한다. 커밋되는 것이 그것이다.

## 표면 예산 — 여유 4자

성공 응답의 형태를 도구 설명에 적으려 했더니 상주 스키마가 **7,500자 예산을
79자 초과**했다. 여유가 원래 **4자**였다(v3.7.5의 58자에서 더 줄었다).

규율대로 교육을 조건부 자리로 옮겼다. 비밀값 치환은 성공 응답에서 더 이상 보이지
않으므로, **실제로 치환이 난 때만** `filtered_note`를 실어 다시 읽으라고 알린다.
상주 스키마는 매 요청에 실리고 이 문장은 그때만 실린다.

안 했으면 안내가 절반이 됐을 것이다 — "`filtered`가 비지 않았으면 저장본이
다르다"고 알려 주고 저장본 볼 방법을 안 주는 상태.

## 남은 것

1. **읽기 빈도를 재야 한다.** 전문이 안 오면 다음 통합 때 읽기가 늘어 절약을
   잠식할 수 있다. 현재 `scope_memory`는 쓰기 212 대 읽기 23건이다. 같은
   파이프라인으로 재고, 늘면 되돌린다. **이것이 이 판의 판정 조건이다.**
2. **승격이 일어나지 않는다(#20).** 상한을 "승격 문턱"이라 선언했는데 상한 초과
   41개 에피소드 중 38건(93%)이 잘라서 통과했다. 진짜 삭제된 88줄 5,713자에
   세션 상태는 0줄 — 전부 지식이었다. 원인은 불복종이 아니라 **가격**이다:
   삭제 0토큰, 승격 5,000~7,000토큰.
3. **처방은 앵커 경로다.** Claude Code 하네스의 `Edit`는
   `(file_path, old_string, new_string, replace_all)` 하나로 돌고 문서 해시가
   없다 — 앵커가 곧 낙관적 잠금이다. 같은 파일을 두 방식으로 건드린 523개에서
   **부분 편집이 전문 치환의 0.119배**였고 실패율은 오히려 낮다(2.2%).
   `update_node`에 `old_text`/`new_text`를 열면 승격이 ~600~800토큰이 된다.
   근거는 이미 osk 안에 있다 — 엣지는 이미 델타로 돈다.
4. **`create_node` 실패율 15.5%**를 아직 안 봤다. 사유가 `other_violation`으로
   뭉쳐 있어 갈라야 한다.
