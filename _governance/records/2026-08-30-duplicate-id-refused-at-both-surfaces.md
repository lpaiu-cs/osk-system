# 겹친 id 앞에서 고르지 않는다 — v3.7.2

## 적용 시 반드시 할 것

**데몬은 프로세스째 멈춘다. `Stop-ScheduledTask`만으로는 멈추지 않는다.**
예약 작업이 `cmd /c ... pythonw.exe ...` 꼴이라 작업 인스턴스를 끝내도 손자
`pythonw`가 살아남아 싱글턴 잠금을 쥔 채로 남고, 갱신이 fail-closed로 멈춘다.

```powershell
Get-CimInstance Win32_Process -Filter "Name LIKE 'python%'" |
  Where-Object { $_.CommandLine -like '*sync_daemon*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

프로세스를 셀 때 **하나를 둘로 세지 않는다.** venv의 `python.exe`/`pythonw.exe`는
베이스 인터프리터를 자식으로 띄우는 **런처 스텁**이라 하나가 둘로 보인다.

v3.7.0부터 판본 관문이 서 있으므로 MCP 서버 재기동을 잊어도 안전하다 —
낡은 프로세스가 자기 다음 쓰기에서 스스로 거부된다.

## 이 판이 어디서 나왔나

v3.7.2로 열었던 **규모 심의**의 산물이다. 물은 것은 "무엇을 지을까"였다 —
id→이름 지도를 둘까, 검색을 프로세스 밖으로 뺄까, 전역 잠금을 쪼갤까.

opus·fable·gpt 3자에게 서로의 답을 모르는 상태로 의뢰했고, **셋 다 지도
제안을 기각**하면서 **아무도 시키지 않은 것을 찾아 왔다** — 지금 돌고 있는
판에 자료 손실 경로가 있다는 것. 셋이 각자 재현했고 여기서도 재현했다.

그래서 이 판은 심의의 답이 아니라 **심의가 찾아낸 결함의 수선**이다. 규모
대응(§4 — id 무작위부 8자, `derived-from` 이름 표기)은 v3.7.3으로 간다.

## 무엇이 잘못돼 있었나

같은 `id`를 가진 노드가 둘일 때 **읽기와 쓰기가 서로 다른 파일을 골랐다.**

| 경로 | 고른 것 |
|---|---|
| `read_node(id)` | 자체 순회의 **첫** 일치 |
| `by_id` → `_live_locate(id)` | 사전 덮어쓰기의 **마지막** |
| `signatures.locate_by_id` | 첫 일치 |

동점 규칙이 셋으로 갈려 있었다. 그리고 중복의 실제 발생원이 **파일 복제**
(옵시디언 "사본 만들기", 백업 복원, 병합 충돌의 수동 해결)이므로 두 파일은
**바이트가 같다** — `expect_hash`가 통과한다. 재현:

```
read_node(id)     → dup-orig 1.md        ← 에이전트가 이 내용을 읽고
update_node(id, expect_hash=읽은해시) → ok, dup-orig.md 갱신
  dup-orig 1.md   본문 = '본문 하나'      ← 읽은 쪽. 안 바뀜
  dup-orig.md     본문 = '바뀐 본문'      ← 읽지 않은 쪽이 바뀜
```

`_live_locate`는 **같은 실패를 이름에 대해서는 명시적으로 막고 있었다** —
*"읽기(색인)와 쓰기가 서로 다른 쪽을 고르면 에이전트가 본 파일과 고쳐지는
파일이 달라진다."* 그 방어가 id에는 없었다. 이 결함은 v3.6.0에도 있었다.

## 무엇을 고쳤나

**동점 규칙을 통일하는 것으로는 부족하다 — 겹쳤으면 고르지 않는다.**

- `graph.parse_all`이 **`dup_ids`를 집계**한다(`dup_stems`의 id판, 같은 이유로
  판독 실패 파일은 세지 않는다).
- `graph.resolve`의 id 갈래가 중복이면 `('ambiguous',)` — 이름 갈래와 같은 답.
- `write._live_locate`가 중복 id를 **거부**한다.
- `mcp_server.read_node`가 자체 순회를 버리고 **쓰기와 같은 `by_id`**로 풀고,
  중복이면 거부한다.
- `signatures.locate_by_id`가 중복이면 `None`(서명 판정에서 fail-closed).
  생산 호출자는 없지만 규칙이 갈린 채 두면 다음 호출자가 함정을 다시 연다.

중복 id는 표면이 만들 수 없다 — 언제나 외부 기원이므로, **표면이 임의로
한쪽을 택하는 것이 더 나쁘다**(이름 중복에 적용해 온 규율과 같다).

검증기의 전역 id 중복 검사는 그대로 둔다. 그것이 **고치라고 말하는** 그물이고,
이번 판은 **고치기 전까지 손대지 않는** 관문이다.

## 시험에 무엇을 넣었나

예제가 아니라 **불변식**으로 적고, 무엇을 망가뜨리면 실패하는지를 시험 자신에
적었다.

- 겹쳤으면 읽기는 노드를 내주지 않고, 쓰기는 거부하며, **어느 쪽 바이트도
  바뀌지 않는다.**
- 세 해석 경로가 모두 고르지 않는다.
- 중복이 해소되면 종전대로 동작하고, **읽기와 쓰기가 같은 파일**을 가리킨다.

수트 873 통과 / 기지 실패 5(Windows·release 계열).

**뮤테이션 검출 4/5.** 다섯째(`read_node`를 구판 순회로 되돌림)는 **동치
뮤턴트**다 — 중복 거부가 먼저 서므로 그 뒤의 조회가 무엇이든 관측 가능한
차이가 없다. 즉 보호를 하는 것은 **거부**이고 동점 규칙 통일은 그 위의
여벌이다. 그것을 잡으려면 거부를 우회하는 시험을 지어야 하는데, 그건 계약이
아니라 구현을 시험하는 것이라 짓지 않았다.

## 심의에서 함께 나온 것 — v3.7.3 이후의 재료

이번 판에 넣지 않았으나 3자가 공통으로 지목했고 기록해 둔다.

1. **제출 수치 셋이 기각됐다.** Searcher 메모리 150 MiB는 `tracemalloc`
   추적량이라 실제 RSS를 **5~8배 과소평가**했고(실측 0.8~1.5 GiB/프로세스),
   합성 본문이 `"본문 " * n`이라 **어휘 다양성이 사실상 0**이었다 — 크기
   분포는 흉내 냈는데 BM25 비용을 정하는 것은 고유 토큰 수다. "26벌에
   3.9 GB"는 **18~31 GB**로 읽어야 한다.
2. **전역 잠금의 최대 보유자는 `create_node`가 아니다.** `sync_daemon._once`가
   같은 `osk-mutation.lock`을 쥔 채 git pull/push의 네트워크 왕복까지 지나간다
   (최악 ~120초). 잠금 입도를 쪼개도 최악값은 안 움직인다.
3. **읽기 통로가 측정에 없었다.** 어떤 쓰기든 지문을 무효화하므로 각
   프로세스가 다음 읽기에서 독립적으로 전수 판독을 문다 — 잠금과 달리
   직렬화되지 않고 **곱해진다.** 그리고 `overview`·`read_node`도 `_s()`를
   부르므로 "검색 안 하는 서버는 검색 메모리를 안 잡는다"가 성립하지 않는다.
4. **§0의 "쓰는 동안 나머지 전부가 선다"는 틀렸다.** 읽기는 `mutation_lock`을
   잡지 않는다. 서는 것은 동시에 쓰려는 쪽뿐이다.
5. **`record_move`는 조건부로만 기록한다**(보호영역이 걸렸거나 기존 이동
   이력이 있을 때). 이동 대장조차 완전하지 않으므로 대장 재생으로 지도를
   세우는 안은 뿌리부터 성립하지 않는다.
6. **경로형 위키링크는 이동에 끊어진다.** v3.7.3의 노드 근거 표기는
   **맨이름형만** 쓴다. 그리고 실 vault의 **본문 Link 15건이 id 표기**라
   함께 옮기지 않으면 `resolve`의 id 갈래가 식지 않는다.
7. **미검증으로 남은 것**: 옵시디언이 개명 시 frontmatter 위키링크를
   재작성하는가. v3.7.3의 "증분 비용 0" 논거가 여기 걸려 있으므로 78개
   이관 전에 실기에서 확인한다.
