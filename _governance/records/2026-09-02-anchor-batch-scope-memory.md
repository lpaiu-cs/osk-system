# 앵커가 해시를 대신한다 — §9-2 4항 개정의 결정기록

Mechanism §9-2 4항을 "전체 치환만"에서 "전체 치환 또는 앵커 일괄"로 개정한
근거다. 조문은 규칙만 담고, 그 규칙을 낳은 실측과 비교는 여기 둔다.

## 무엇을 재다가 여기까지 왔나

토큰 감사(#20·#21, v3.9.x)는 osk 도구의 **응답 크기**를 표적으로 잡았고 17.2%를
걷었다. 그런데 그 17.2%의 분모가 전체 예산의 0.92%였다. 14일 창 전체는
8,877,143,040토큰이고 그중 **캐시 읽기가 97.2%**(가격가중 69.1%)다. 대화에 얹힌
토큰 하나가 이후 평균 **39번** 다시 읽힌다.

그러면 비용의 단위는 응답이 아니라 **턴**이다. osk 호출 721건이 554턴을 썼고,
그 시점 프롬프트 평균이 508,466토큰이라 턴 하나가 문맥 재독으로만 ~50,847단위를
문다. 페이로드 전체(0.92%)의 **2.4배**(2.25%)다.

## 턴이 어디서 새는가 — 554턴 분류

| 분류 | 턴 | 전체 대비 |
|---|---:|---:|
| 필요 | 345 | 1.34% |
| 재시도 | 128 | 0.57% |
| 묶을 수 있었음 | 56 | 0.23% |
| 읽고 바로 쓰기 | 14 | 0.06% |
| 짝 다리 | 11 | 0.05% |

재시도 128 중 **84가 scope 기억 상한 초과**다. 그리고 통합 호출 235건 중
**단독 턴이 235, 동승이 0** — 통합은 예외 없이 자기만의 턴을 쓴다.

## 상한 초과는 못 세서가 아니라 꽉 차서다

상한 초과 거부 87건의 응답을 전수 파싱했다.

| 거부 시점 | |
|---|---|
| 저장본 크기 | 중앙값 **1,487 / 1,500** (p25 1,467) |
| 이미 1,400자 이상 | **79건 / 87 = 91%** |
| 남은 자리 | 중앙값 **13자** |
| 넣으려 한 양 | 중앙값 **85자** |

13자 자리에 85자를 넣으려 했다. 세는 능력의 문제가 아니라 **먼저 비워야 하는데
안 비운 것**이고, 안 비우는 이유는 #20이 밝힌 그것이다 — 비울 것이 결론 난
교훈이라 지우기를 꺼린다. 거부 에피소드 41건 중 38건(93%)이 잘라서 통과했고,
증류 없이 잘려나간 88줄 5,713자에 세션 상태는 0줄이었다. 최장 8연속 거부.

전체 치환은 이 병을 키운다. 49자를 넘기면 1,500자를 통째로 다시 뱉어야 하고,
그 재시도가 또 넘기면 또 통째로다. 한 번의 통합에 시도가 중앙값 2.0회 든다.

## Hermes가 이미 푼 문제였다

`NousResearch/hermes-agent`의 `tools/memory_tool.py`. osk는 Hermes의 상한(2,200·
1,375자)은 가져오고 **저장 모델은 가져오지 않았다** — 그 저장 모델이 이렇다.

- 엔트리 단위 연산 `add`/`replace`/`remove`. `replace`·`remove`는 `old_text` —
  *"a short unique substring identifying the existing entry"* — 를 받는다.
  앵커다. 이름까지 같다.
- **일괄 연산, 전부 아니면 전무, 상한은 순결과에만.** 도구 설명 원문:
  *"the char limit is checked only on the FINAL result — so a single call can
  remove/replace stale entries to free room AND add new ones, even when an add
  alone would overflow."* 코드 주석이 이유를 적는다: *"the multi-turn
  consolidate-then-retry dance that re-sends the whole conversation context
  several times."* 우리가 잰 것을 그쪽이 이름 붙여 뒀다.
- **`_MAX_CONSOLIDATION_FAILURES_PER_TURN = 3`.** 넘으면 재시도 지시를 빼고
  *"Stop retrying — leave memory unchanged and continue with your reply"*.
  근거: *"a failed memory side effect must never block the turn's reply."*
- 거부문이 `current_entries`를 싣고 *"Reissue as ONE batch"* 를 지시한다.
- 케이던스는 없다 — *"save proactively when the user states a preference…"*.

Claude Code의 자동 메모리는 다른 답을 갖고 있다: 상주하는 것은 `MEMORY.md`
**색인**(200줄/25KB)뿐이고 내용은 주제 파일에 있어 필요할 때 읽는다. 상주와
저장이 다른 물건이다. osk의 scope 기억은 1,500자가 상주 크기이자 저장 상한이라
"넘친다"가 곧 "잃는다"가 된다. 이 방향은 이번 개정에 넣지 않았다 — scope 기억이
무엇인지를 바꾸는 일이라 따로 다룬다.

## 결정 — 파싱하지 않고 앵커로

Hermes식 평평한 엔트리 목록은 파일 형식을 바꾸고 절(`##`)과 감긴 불릿을 잃는다.
대신 **파일은 그대로 두고 연산만 앵커로 받는다** — 노드에 연 앵커 편집(§6-2
4항, `920edf9`)을 일괄로 넓힌 것이다.

- `edits = [{old_text, new_text}, …]`. 각 앵커는 그 시점 작업본에 정확히 한 번.
- 전부 아니면 전무. 상한은 순결과에만.
- 해시 불요 — 앵커가 "고칠 자리를 봤다"는 증거다.
- 원소는 엔진이 정하지 않는다. 호출자가 앵커로 그때 정한다.
- 연속 3회 거부 시 재시도 지시를 거둔다. 세션 키 단위, 프로세스 안에서만
  센다(엔진은 하네스 턴을 보지 못한다). 성공이 지운다.

부분 연산을 금했던 §9-2 4항의 근거 — "무엇을 버릴지 엔진이 모른다" — 는
그대로 지킨다. 버리는 결정은 호출자가 같은 호출 안에서 하고, 엔진은 어떤
경우에도 스스로 버리지 않는다.

## 이것이 여는 것

| | 지금 | 앵커 일괄 |
|---|---|---|
| 통합 1회 | 1,500자 전문 재발화 | `remove` + `add` ~150토큰 |
| 넘침 | 거부 → 전문 다시 → … (중앙값 2회, 최장 8) | 거부문 보고 한 호출로 빼고 넣는다 |
| 승격 | ~5,000토큰이라 안 함 (7%) | 기억 `remove` + 노드 앵커 `update_node`, 같은 턴 |
| 동승 | 1,500자짜리라 별도 턴 (단독 100%) | 150토큰이라 다음 도구 호출에 실린다 |

재시도 턴이 구조적으로 사라지지는 않는다 — 호출자가 여유를 무시하고 `add`만
보내면 여전히 거부되고 그 턴은 값을 문다. 바뀌는 것은 셋이다: 훅이 "여유 N자"를
보여 주니 첫 시도가 맞을 확률이 오르고, 재시도해도 페이로드가 150토큰이고,
실패 상한이 8연속을 끊는다.

## 함께 바꾼 것

- **5항** — 앵커 불일치를 전문 싣는 거부에 넣었다. 저장본이 호출자가 모르는
  것이 돼 있다는 뜻이라 해시 불일치와 같은 자리다.
- **케이던스 훅** — 9턴에 전문·해시·여유를 주입하고 "다음 도구 호출에 함께
  실어라"를 지시한다. 15턴까지 기억이 갱신되지 않으면 단독 턴을 허용하는
  지시를 낸다. 기억이 바뀌면 계수를 처음으로 돌린다.
- **6항은 그대로다.** "정리 먼저, 증류 나중"은 앵커 일괄에서 같은 호출 안의
  순서로 성립하고, 잡동사니가 노드가 되는 것을 막는 우려는 유효하다.

순간이 아니라 안 막힌 순간에 오고, 요구하는 행동의 값이 5,000토큰이 아니라
150토큰이다. 되는지는 재 봐야 안다.
