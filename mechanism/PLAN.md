# mechanism 사양 — 착수 계획 (draft)

## 0. 이 문서의 지위

이 문서는 **계획**이지 활성 규정이 아니다. 시스템의 외부 행동을 결정하지 않으므로
시행령 §15.2가 요구하는 근거 조문 명시 의무의 대상이 아니다. 다만 mechanism 층
전체가 §15 아래 놓이므로, 어느 조문을 실현하려는 계획인지를 frontmatter에
`implements`로 밝힌다.

`implements`는 Predicate Edge가 **아니다**. 헌법 10조 5항상 술어는 구별된 엔진
행동과 함께 비준될 때에만 생기며, 이 필드는 기술적 출처 메타데이터다. 주석백서의
`annotates`와 같은 성격이다.

이 계획은 에이전트가 작성하며 사용자 비준을 요하지 않는다(§15.1). 사용자가 비준할
것은 §6의 G-트랙뿐이다.

## 1. 권한 구조

**사용자가 결정하는 것** — G-트랙(§6) 세 묶음뿐이다.

**에이전트가 결정하는 것** — 아키텍처, 계약, 계수, 모듈 사양, 구현. 통제는
사후로 이루어진다: 브리핑 보고(§12.1), 엔진 상시 검증(§14.11), 개별 변경의 되돌림,
자율권 자체의 회수(§13.3 — **사용자 지시 즉시 효력**).

**독립 검토(codex)가 보는 것** — 아키텍처의 제정·의미 변경, 봉인 계약의 제정·의미
변경, 행동 매개변수의 최초 기본값과 계산 모델, G-트랙 승격물. 새 서명 검증 규칙
버전은 §8.5가 별도 세션의 재현 검증을 **활성화 요건**으로 못 박았다 — 이것만은
권고가 아니라 관문이다.

**상시 게이트** — 모든 mechanism 결정에 삼분류를 적용한다: 시행령이 이미 확정한
집행 의무인가(§4) / 조문에서 도출되는 구현인가 / 도출되지 않아 상향해야 하는가
(§15.3). 셋째에 해당하면 확정하지 않고 올린다. 「참조 자체는 권한을 만들지
않는다」(§15.2)가 이 판단의 기준이다 — 넓은 조문 하나를 인용해 새 정책을 구현이라
부르는 것이 이 구조의 유일한 급소다.

## 2. 문서 구조

```text
mechanism/
  PLAN.md              이 문서
  IMPLEMENTS.yaml      조문 → 주 책임 문서 → 검증 방법. 커버리지의 단일 정본
  ARCHITECTURE.md      모듈 경계·데이터 흐름·집행 의무 매핑·3등급 규율
  adr/                 설계 결정 이력 (되돌린 갈래도 남긴다)
  contracts/
    signed-state-schema/    봉인 계약 — 서명 대상 상태의 논리 구조
    canonicalization/       봉인 계약 — 정규화·해시·버전
    identifiers/            봉인 계약 — 서명 검증에 쓰이는 식별자
    node-envelope/          일반 호환 계약 — 표시·파생 메타데이터
  modules/
    signing/  graph-compiler/  search/  consistency/  briefing/
    harness-adapter/  casebook/  storage-gate/  legacy-migration/
  fixtures/            합성 golden 전용
```

`ARCHITECTURE.md`의 매핑표는 `IMPLEMENTS.yaml`에서 생성하거나 참조한다 — 손으로
관리하는 장부를 둘 두면 어긋난다(위임표를 시행령에서 뺀 이유와 같다).

`IMPLEMENTS.yaml`은 **양방향 검사**를 진다:
1. 시행령의 기계 집행 의무마다 주 책임 문서가 정확히 하나 있는가
2. 모든 활성 mechanism 규정에 정확한 조문과 고정 blob 근거가 있는가(§14.11)

주 책임자는 하나지만 소비자·검증자는 복수일 수 있다 — 하나의 계약을 서명·검색·
컴파일 모듈이 함께 쓴다.

모듈명은 예시다. 아키텍처 확정 전까지는 이름이 아니라 **책임**만 고정한다.

## 3. 변경 규율 — 3등급

| 등급 | 대상 | 규율 |
|---|---|---|
| **봉인 계약** | 정규화·해시·서명 검증 식별자·서명 블록 직렬화 | 버전 공존·비소급(§8.5), golden vector, **별도 세션 재현 검증이 활성화 요건**, 브리핑 |
| **행동 매개변수** | 중심성·검색 강등·전파·라우팅 계수 | 에이전트 조정, 이력 기록, 사용자 주의·라우팅 영향 시 브리핑(머리말·§15.5), 되돌림 |
| **구현 내부** | 모듈 분할·DB·캐시·큐·내부 API·성능 | 에이전트 자율, 테스트·CI. 보고 대상 아님(§15.3) |

경계 원칙: **의미는 시행령, 직렬화는 mechanism.** 무엇이 서명 대상인가(§8.2),
무엇이 봉인을 깨는가(§8.3), 어떤 변환이 의미 비변경인가, 비소급 규칙(§8.5)은
시행령이 정한다. 그 경계를 보존하는 바이트 직렬화·필드 배치·해시 알고리즘·버전
인코딩은 mechanism이 정한다.

`node-envelope`를 봉인 계약에서 뺀 것은 §8.2 자신의 구분을 따른 것이다 — 표시용·
파생 메타데이터는 해시 대상이 아니므로, 필드 하나 추가에 새 봉인 버전을 요구할
이유가 없다.

## 4. 고정된 집행 의무 — 재량이 아니다

아키텍처 설계에서 "구현 재량"으로 착각하면 안 되는 것들이다. 각 항목은
`IMPLEMENTS.yaml`에 주 책임 모듈을 갖는다.

- **§8.1 선확정 4단 트랜잭션** — 순서 자체가 의무다. 파일을 바꾸는 정규화는 (2)에서
  전부 적용, 사용자 확인 뒤 서명 대상 상태 무변경, 해시는 파일 무변경 투영.
- **§1.16 검색의 두 결** — 작업 검색은 미서명 강등 없음·휴면 시계 리셋 없음,
  열람 검색은 둘 다 적용. 의미론이 고정이다.
- **§9.4 중심성 산입의 정본 규칙** — 기초 의존 1회(이중 계상 금지), supported-by는
  기초 의존 **위에** 강한 가중, replaces는 의존 가중 없이 승계, contradicts 가중 0,
  미서명→서명 의존은 산입, 휴면도 산입. 계수 선택으로 이 구조를 무력화할 수 없다.
- **§11.5 서명 Knowledge 노드 불망각 / §11.6 시스템 발의 영구 삭제 금지.**
- **파일 정본 / DB 파생** — 서명 블록(§8.1 말미)과 사건부(§10.4)는 파일이 정본이고
  DB는 재계산 가능한 인덱스다. DB 소실은 복구 가능해야 한다.
- **§10.1 검사기** — hybrid 구성, **LLM 판정은 recommend-only, no veto**.
- **§10.4 사건부의 의미 최소치** — 당사자 상태·충돌 사유·증거 집합·판정·보존 이력.
  필드명과 포맷은 draft로 열려 있다(재량).
- **Workbench 격리** — 전역 질의 제외, PE 없음, 참조 비산입(§5, §9.2).
- **§12.2 처리 의무 없음** — 브리핑은 죄책감 큐를 만들지 않는다. 보고 문턱을
  넓히는 설계는 이 조문에 걸린다.
- **헌법 14조 3항 no-grandfathering** — 구 노드는 미서명 신분으로 배치 가능하되
  검색에서 후보 표기·강등.
- **§8.5 비소급 / §15.2 참조가 권한을 만들지 않음** — 이번 개정 신설.

## 5. 위임 커버리지 — IMPLEMENTS.yaml의 초기 목록

시행령에서 위임표를 뺐으므로 이 목록은 규범이 아니라 **작업 목록**이다. 각 항목은
해당 mechanism 문서가 자기 근거 조문을 역참조하는 방식으로 성립한다.

**PE의 '응집' 반영식은 이 표에 없다** — 시행령이 그 행동을 특정하지 않았으므로
G1이 해소되기 전에는 도출 근거가 없다(§15.2).

**governance 문서의 frontmatter 스키마도 이 표에 없다** — G4 소관이다.

## 6. G-트랙 — 사용자 비준이 필요한 것

| # | 항목 | 성격 |
|---|---|---|
| **G1** | Predicate Edge의 '응집' 반영 양상 | 현행 시행령에서 단일 행동이 도출되는지 해석을 먼저 시도하고, 도출되지 않으면 **시행령 개정**. 해석 기록으로 대체하지 않는다 |
| **G3** | 헌법 11조 3항 Observation 강등 사정거리 / §10.2 '만' 문면 / 서명된 Observation 노드의 존치 출구 | 세 건 모두 행동 범위 변경이므로 시행령 개정 후보 |
| **G4** | governance 문서의 존재론적 지위 + frontmatter 규율 + `governance-vX.Y.Z` 버전 체계 | 기존 "뼈대 후 판정 묶음"과 병합. 범위는 governance 문서 스키마에 한정 — 3-Layer 스키마를 차단하지 않는다 |
| **G2a** | 발효 acceptance criteria | **구현 착수 전** 비준. 뒤에 정하면 결과에 기준을 맞추게 된다 |
| **G2b** | 발효 선언 | 검증 통과 후 별도 비준. mechanism 내용의 총괄 비준이 **아니다** — 기준은 사용자가, 충족 여부는 검증이, 내용의 책임은 에이전트가 진다 |

## 7. 실행 순서와 게이트

```text
[즉시 병렬]
  IMPLEMENTS.yaml + ARCHITECTURE.md 초안      조문 의무 매핑이 먼저
  하네스 실측(§6.5)                            contracts 확정의 게이트
  G4 판정 요청                                 governance 스키마만 차단
  G1 해석 시도 → 미도출이면 개정 후보           응집 반영식만 차단

contracts/ draft → 실측 반영 → 독립 검토 → 확정
  · 발효 전까지 자유 반복. 확정 후에는 §8.5의 버전 공존·비소급이 발효한다
  · canonicalization은 원소별로 나눠 검토: 알고리즘·버전 / UTF-8·Unicode·줄바꿈 /
    YAML typing·중복 키·키 순서 / PE 정규화·대상 식별자 / 포함·제외 필드 /
    round-trip 규칙 / golden vector

modules/ 착수
  · graph-compiler는 참조 의미론을 먼저 확정한다 — cycle/SCC 처리, 다중 경로의
    중복 여부, 노드 수와 가중 비용의 결합, 정지된 PE·미서명·휴면 처리,
    replaces 승계의 시작·종료 조건
  · 합성 fixture로 브리핑 폭주·과도한 은폐가 없는지 확인한 뒤에만 계수를 활성화한다

G2a 기준 설계·비준 → 구현 → 검증 → G2b 발효 선언
```

**게이트는 전역이 아니라 항목별로 건다.** G1은 응집 반영식만, G3는 영향받는
검색·보존 계약과 계수만, G4는 governance 스키마만, 하네스 실측은 쓰기 경로·저작
표기 관련 계약만 막는다. 전체 contracts를 하나의 게이트로 묶으면 병렬성과 권한
경계를 둘 다 잃는다.

**legacy 이행**은 G2a acceptance criteria에 포함한다 — 구 vault 노드의 dry-run
분류표와 사용자 승인 write set을 요구한다(헌법 14조 3항, §11.6).

## 8. fixture 원칙

- 공개 golden fixture는 **처음부터 합성**으로 만든다.
- 실제 vault 표본은 **비공개 calibration 전용**이다. 익명화해도 그래프 위상 자체가
  구조적 정보를 노출한다.
- 공개 산출물에는 집계 결과만 낸다.

## 9. 릴리스와 발효

둘은 다른 사건이다. 통치 문서는 엔진 없이 `governance-v1.0.0`을 낼 수 있고,
발효는 acceptance criteria 통과 후의 별도 판정이다.

릴리스 매니페스트(`RELEASE.yaml`)는 네 정본의 blob과 bump 사유·호환성 검토 결과를
고정한다. 전파 규칙 — **X**(헌법 변경): 하위 전부 재검사. **Y**(시행령 변경):
mechanism과 **두 주석백서 모두** 재검사(헌법 주석도 시행령을 다수 인용한다).
**Z**: 규범 의미·호환성 경계 불변, 전파 없음.

G2b 발효 기록은 governance 릴리스뿐 아니라 **acceptance criteria를 통과한
mechanism·엔진 구현 릴리스도 함께 고정**한다. 문서만 고정하면 어느 코드가
통과했는지 특정할 수 없다.

버전 체계 자체는 G4에서 확정한다.

## 10. 알려진 위험

**해석적 확장.** 사전 관문이 사후 통제로 바뀐 대가다. 조문을 늘려 읽어 실질적 새
행동을 "구현"이라 부르는 것 — §15.2가 이를 겨냥하지만 판단은 결국 에이전트가
한다. 완충: 헌법 13조 2·3항의 상시 울타리(중심부·모호 사안은 구조적으로 위임
불가), §12.1 보고와 §14.11 활성화 검증, 자율권의 즉시 회수. 새는 곳이 발견되면
판례로 좁힌다(cold start 보수 원칙).

**계수의 cold start.** 사용자가 계수 비준에서 빠지는 만큼 최초 기본값이 가장
위험하다. 표본·fixture 없이 정하면 브리핑 폭주, 광범위 효력 정지, 또는 중요한
미서명 지식의 과도한 은폐가 발생할 수 있다. §7의 fixture 게이트가 이를 막는다.

**서명 비결정성.** 하네스별 YAML·Unicode·순서 차이로 같은 상태의 해시가 갈라지는
것. canonicalization 원소별 검토와 golden vector가 대응이다.

**구 엔진과의 불일치.** `legacy` 브랜치의 `90_Engine`과 현행 ltm-vault MCP 서버는
구 9술어 온톨로지 기반이라 osk-system과 맞지 않는다. 재작성이 필요하며 이행 경로는
`legacy-migration`이 진다.
